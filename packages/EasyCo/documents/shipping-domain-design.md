# Shipping Domain Design — zones, classes, methods, and the doors a carrier plugs into

**Status:** Draft v1 — approved scope. **Stage 1 (entities and persistence) is implemented** (commit `0fdbfad`); stage 2 (`Order` carries shipping, §7) is in progress; stages 3–5 are not started. The order of work is in `shipping-and-checkout-queue-note.md`.
**Closes / supersedes:** `product-shipping-fields-note.md`'s open questions 1–4 (that note stays as the record of what was already true before this). Resolves `checkout-domain-design.md` §3/§10's standing statement that `Order.total` carries no shipping component.
**Builds on:** `address-domain-design.md` (the `PICKUP_POINT` shape this design depends on and does not change), `checkout-domain-design.md` §8.3 (the two-phase placement this inserts into), `payment-domain-design.md` (whose adapter/resolver shape the provider contracts here deliberately mirror), `promotions-domain-design.md` (unchanged by this document — see §8).
**Origin:** the domain owner's requirement, stated directly: this is not being built only for his own shop, so it has to be a working shipping system — zones, classes, a fixed amount, a free-shipping threshold, free or priced delivery driven by a product's class, all varying by zone — **with the foundation first and the doors for anyone to plug an extension into**. Econt / Speedy / BoxNow are explicitly NOT part of it; they come after, through those doors.

Two platforms and the Bulgarian market were checked before any of this was written:

- **WooCommerce** models shipping as ordered **zones** → **methods** → **classes**: zones are matched against the customer's address top to bottom, the first match wins, and each customer matches exactly one zone; the built-in methods are only three (flat rate, free shipping, local pickup); classes are assigned per product and let a method charge differently per class. The skeleton is sound and is adopted below. The domain owner's own criticism is about the *reach* of those three methods, not the structure: no office selection, no weight or volume calculation, no label from the carrier's API — which is exactly right.
- **Shopify** keeps the same skeleton but ships three *kinds* of rate rather than one: flat, weight-based, and value-based (price thresholds — i.e. the free-shipping threshold as a first-class concept). More importantly it has what Woo lacks: a **carrier service** callback, where an external provider returns live rates for a request, with response caching and fallback rates when the provider times out. That callback is the model for §6's provider contract.
- **The Bulgarian market confirms both.** An entire industry of paid apps (Dostavi.bg, Izprati, CourierHub, ShipBG, Fulfillvam) exists specifically to add office/locker selection from a map, real carrier pricing, and label generation to Shopify and WooCommerce — the three things neither does natively. That is evidence the work below is the differentiator rather than a reimplementation of something already solved.

## 1. Scope, and the three doors

Built here: `ShippingClass`, `ShippingZone`, `ShippingMethod`, rate resolution at checkout, and `Order` finally carrying a shipping amount.

**Not built here, but named and contracted, so a carrier can be added later without reopening this design:**

1. `ShippingRateProvider` — a live rate from a carrier.
2. `PickupPointProvider` — the list of a carrier's offices and lockers.
3. `ShipmentLabelProvider` — the waybill (товарителница).

Each is a contract with zero implementations in V1. They exist so that the Econt/Speedy/BoxNow work is an *addition*, not a redesign. The project already has the exact precedent for this shape: `PaymentMethodAdapter` is bound under named container keys, resolved by `PaymentMethodAdapterResolver`, which refuses an unknown method rather than falling back to a default — because silently charging someone through a method they did not choose is worse than a loud failure. The same rule applies to carriers, for the same reason.

## 2. What already exists, verified rather than assumed

- **`Catalog\Variation` already carries the physical facts**: `shippingClass` (today a plain nullable string), `weightGrams`, `lengthMm`, `widthMm`, `heightMm` — integers in grams and millimetres on purpose, so no float drift appears between Catalog and Shipping. Columns, both write paths and both read paths are done. Only the admin UI is missing.
- **`Address` already models a pickup point properly**: `STREET_ADDRESS` or `PICKUP_POINT`, the latter carrying `carrierCode`, `pickupPointReference` and `settlement`, deliberately carrier-agnostic. **This design does not change `Address` at all.** It is the single most valuable thing already in place, because office delivery is where the two big platforms fail and where Bulgarian commerce actually lives.
- **`Order` has no shipping anywhere**: `subtotal_minor`, `discount_minor`, `total_minor`, and `Order::create()` computes `total = subtotal - discount` itself, refusing a separately supplied total. §7 changes exactly this and nothing else about the entity.
- **`Catalog\Product` has nothing**: no physical properties, no columns. So the SIMPLE product's shipping fields are not a UI-only task (§3.2).

## 3. `ShippingClass` — a real entity, not a free string

```
ShippingClass                                  (package EasyCo\Shipping)
├── id
├── name                  merchant-facing: "Обемисти", "Чупливи", "Малки пратки"
├── code                  unique, stable, machine-facing; what a Variation refers to
└── description           nullable, for the merchant's own memory
```

Today `Variation.shippingClass` is a nullable free-text column with no list behind it, so no `Select` can read from one and two variations can disagree by a typo. It becomes a reference to this entity's `code`.

**Deliberately `code`, not `id`:** a class is referenced from `Catalog`, and this project's rule is that cross-domain references are plain values, never foreign objects. A stable string code keeps `Catalog` free of any dependency on `Shipping`, exactly as `Address.carrierCode` is a plain string today. Migrating the existing column is therefore a data concern, not a structural one — existing values become codes.

**No class = the method's default rate.** Absence is a normal, supported state, not a configuration error: most products in a boutique need no class at all.

### 3.1 Combining classes in one cart — THE MOST EXPENSIVE CLASS WINS

Domain-owner decision, and the one rule most likely to be "improved" later by someone who assumes summing is more correct:

> **When a cart holds items of several shipping classes, the order is charged the single most expensive of those classes' rates — not their sum.**

The reasoning is the merchant's own: one parcel usually goes out, and charging the customer the sum of three class rates for one parcel overcharges them. If the real dispatch turns out to need more, the merchant edits the placed order and adjusts it there — the order editing flow already exists for exactly this kind of after-the-fact correction.

Summing, per-parcel splitting, and per-item charging are all explicitly rejected for V1. Whoever revisits this should read this paragraph first.

### 3.2 The product side needs real work, not a form field

`Variation` is ready; `Product` is empty. A SIMPLE product has exactly one variation, so it *can* carry its values there — and that is the recommended route, since it keeps one storage shape for both product types and avoids a second source of truth that would need a precedence rule. The SIMPLE form writes to its single variation's fields.

If the decision later goes the other way (product-level values with per-variation overrides), that is a migration plus a precedence rule and must be designed deliberately, not drifted into.

## 4. `ShippingZone` — ordered, first match wins

```
ShippingZone                                   (package EasyCo\Shipping)
├── id
├── name                  "България", "София-град", "Европейски съюз"
├── sortOrder             the match order; lower is checked first
├── countryCodes          the countries this zone covers (uppercase ISO alpha-2)
├── settlementNames       nullable — optional narrowing: a list of settlement
│                         names, stored as entered ("София", "гр. София")
└── postcodes             nullable — optional narrowing: a list of postcodes,
                          normalized at construction (trim, ALL whitespace
                          removed, uppercase; ^[A-Z0-9-]{2,12}$)
```

Narrowing is what lets "София-град" sit above "България". The two lists replaced a single free-form `settlementPatterns` list that mixed names and postcodes; with nothing in the data to tell them apart, a postcode could be mistaken for a name. A zone with neither list is not narrowed at all.

**Matching rule, taken from WooCommerce because it is proven and a merchant can hold it in his head:** zones are checked in `sortOrder`, the first one matching the delivery address wins, and **an order matches exactly one zone**. Narrow zones are placed above broad ones.

**A zone matches the address when the country matches AND EITHER of these holds:** the zone has **no settlement names and no postcodes** (not narrowed), **or** the address's settlement matches one of the zone's **names**, **or** the address's postcode matches one of the zone's **postcodes**. A street address's **`city` is its settlement**; a pickup point's **`settlement`** is its settlement. **The delivery country is a validated ISO 3166-1 alpha-2 code on EVERY address, a `PICKUP_POINT` included** (owner decision D1, final; built in stage 3.0b), so the country test applies to a pickup point exactly as to a street address. The store country (`site.country`) is only the **default the checkout form preselects**; it is never substituted for a missing country. A pickup point has **no postcode**, so a zone narrowed by postcodes alone cannot match it. The matcher is built (stage 3a); its exact rules follow.

**An address matching no zone cannot be shipped**, and checkout refuses with a clear message rather than silently offering nothing or falling back to a free delivery. There is no implicit "rest of the world" zone: a merchant who wants one creates a zone with no narrowing and puts it last, which is the same thing but visible in his own configuration rather than hidden in the code.

**Which address is matched:** the order's delivery address. For a `PICKUP_POINT` address the `settlement` field is matched, since a pickup point has no street address of its own — another reason `Address` was right to carry it.

**Settlement matching (addendum to §4, built in stage 3a).** Settlement **names** are *stored as entered* and normalized only when matching, on BOTH sides of the comparison (each zone name and the destination's settlement), by a `SettlementNameNormalizer` (`EasyCo\Shipping\Contracts`, `normalize(string): string`). **Postcodes** are normalized once, when the zone is built, and the destination's postcode is put through the same function (`PostcodeNormalizer`): trim, remove ALL whitespace (ASCII, NBSP and every other Unicode separator), uppercase — "sw1a 1aa" and " SW1A1AA " both become "SW1A1AA".

*The neutral rules* (`NeutralSettlementNameNormalizer`, used for every locale without rules of its own), in this order:
1. Unicode NFC, so a decomposed "й" (и + U+0306) equals the composed "й";
2. case **folding** (`MB_CASE_FOLD`), not just lower-casing;
3. every run of whitespace — including NBSP and other Unicode separators — becomes ONE space, and the ends are trimmed;
4. the dash variants U+2010 ‐, U+2011 ‑, U+2013 – and U+2014 — become "-".

Nothing else: **no prefix stripping and no transliteration** — "Sofia" and "София" are different names, and a merchant lists each spelling he wants. Malformed UTF-8 normalizes to the empty string, which matches nothing (the destination is customer-supplied, so this is a refusal, never an exception).

*The Bulgarian rules* (`BulgarianSettlementNameNormalizer`): the neutral steps, plus stripping **one** leading settlement-type prefix: "гр." and "с." (with or without a space after the dot), and "гр ", "град ", "с ", "село " (these four need the following space, so "Градец", "Сопот" and "Селце" are untouched), case-insensitively. So "гр. София", "ГР. СОФИЯ", "град София" and "София" are the same name. **Deliberately NOT stripped:** "кв." (квартал), "ж.к." (жилищен комплекс) and every other prefix — they name a district inside a town, not a settlement, and stripping them would equate "кв. Лозенец" with the town "Лозенец".

**The comparison is equality after normalization — never a substring, prefix or fuzzy match.** A blank settlement or postcode matches nothing. A pickup point has no postcode: any postcode given with a pickup point is ignored.

**The matcher** (`EasyCo\Shipping\Matching\ZoneMatcher`, pure: no framework, no Hook, no Address/Order/Cart) takes the zones, a `ZoneDestination` value (`countryCode`, `settlement`, `postcode`, `isPickupPoint`) and the normalizer. It orders the zones by `sortOrder` ascending then `id` ascending (numerically), applies the rule above, and returns a `ZoneMatchResult`: the first matching zone, or the explicit refusal `no_zone_for_destination` — never null and never an empty list.

**Choosing the normalizer (app layer).** `App\Services\SettlementNormalizerResolver` picks it by the **store locale** (`StoreLocale::current()`, not `App::getLocale()`, which the `api` group never sets). It looks the locale up in the container under the name **`shipping.settlement_normalizer.<locale>`** — the whole locale first (`pt_br`), then its language (`pt`); `bg`, `bg_BG` and `bg-BG` all reach the Bulgarian one. A locale with no binding, and an unknown or empty locale, gets **`shipping.settlement_normalizer.neutral`** (owner decision D3: never a refusal). **There is no list of locales in core:** the package registers only `neutral` and `bg`, and **an extension package adds a locale by binding its own implementation of the contract under that name** (`$this->app->bind('shipping.settlement_normalizer.ro', RomanianSettlementNameNormalizer::class)`) — nothing in core is edited.

## 5. `ShippingMethod` — what the customer actually picks

```
ShippingMethod                                 (package EasyCo\Shipping)
├── id
├── zoneId                the zone this method is offered in
├── name                  what the customer sees: "Еконт до офис", "Доставка до адрес"
├── kind                  FLAT | FREE | PER_CLASS | CARRIER
├── sortOrder             the order they are listed in; the first is preselected
├── isActive
├── amountMinor           FLAT: the price. PER_CLASS: the price when an item has
│                         no class, or its class has no rate here
├── classRates            PER_CLASS: an amount per ShippingClass code
├── freeAboveMinor        nullable — a free-shipping threshold (§5.1)
├── carrierCode           CARRIER only: which provider to ask (§6)
└── requiresPickupPoint   whether choosing this method means choosing an office
```

**The four kinds, and why only four:**

- **FLAT** — one price for the zone. The overwhelmingly common case.
- **FREE** — zero. Kept as its own kind rather than "FLAT with 0" so a merchant reading his configuration sees intent, and so the checkout can label it plainly.
- **PER_CLASS** — the rate depends on what is in the cart (§3.1's most-expensive rule). This is what makes "free if it is in this class, 5 € if it is in that one" real.
- **CARRIER** — this method's price is not configured here at all; it is asked for, live, through `ShippingRateProvider` (§6). No implementation in V1, so no merchant can select it yet — the kind exists so the door is part of the model rather than bolted on later.

**Weight-based rates are deliberately NOT a kind in V1** — domain-owner decision, "later". The data is already there (`weightGrams` on every variation), so adding a `WEIGHT` kind later is one enum case, one rate table and one branch in the calculator. It is deferred, not designed out: §10 records it.

### 5.1 The free-shipping threshold is measured AFTER the discount

Domain-owner decision, recorded explicitly because the opposite reading is equally defensible and someone will raise it:

> **`freeAboveMinor` is compared against the order's `subtotal - discount`, i.e. what the customer actually pays for goods — not against the pre-discount subtotal.**

So a 100 лв. cart with a 20% code and a 90 лв. threshold does **not** get free shipping: the customer is paying 80 лв. The merchant's exposure follows the money he actually receives, which is the honest basis for a giveaway.

The customer must be able to see why, so the storefront shows how much more is needed, computed on the same basis. A threshold that silently moves when a code is applied is worse than no threshold.

### 5.2 The rate calculator: the exact rules (built in stage 3b)

`EasyCo\Shipping\Rating\ShippingRateCalculator` is pure: its input is a `RateRequest` — `currency`, `goodsAfterDiscountMinor` (the shared `CartPricing` figure, §5.1) and a list of `RateLine {shippingClass: ?string, quantity: int}`; an empty list of lines is refused — and its output is, per method, a `MethodRate`: either a price in minor units or "needs a carrier quote". It is given the matched zone's methods and returns the **active** ones only, ordered by `sortOrder` ascending, then `id` ascending **numerically** (2 before 10).

All of it is **per order, never per unit**:

- **FREE:** 0, whatever the cart.
- **FLAT:** `amountMinor`.
- **PER_CLASS:** every line takes the rate of its class on this method. A line with **no class** (null or blank), or whose class **has no rate on this method**, or whose class code **Shipping does not know** (`Variation.shippingClass` is still free text, and codes are compared exactly, never case-folded), takes the method's `amountMinor` — the **fallback**. The order is charged the **single highest** of those per-line rates (§3.1), **never their sum**, and **quantities do not multiply it**: classes rated 3, 7 and 5 charge 7, not 15. A rate of 0 is valid; all lines at 0 charge 0.
- **Free-shipping threshold (FLAT and PER_CLASS):** when `freeAboveMinor` is set and `goodsAfterDiscountMinor >= freeAboveMinor`, the charge is 0. **It is `>=`: an order exactly at the threshold is free** (7999 against 8000 is charged; 8000 and 8001 are free).
- **CARRIER:** "needs a carrier quote" — never priced locally, not even 0. How `freeAboveMinor` combines with a live quote is still open (queue note) and is deliberately **not** applied.

The value objects are named `RateRequest`, `RateLine` and `MethodRate` so they do not collide with the §6 provider types (`ShippingQuote`, `ShippingContext`, …), which arrive in stage 3c.

## 6. The doors: three contracts, zero implementations

All three live in `EasyCo\Shipping\Contracts`, are resolved by code through named container bindings, and **never fall back to a default provider** — the exact posture `PaymentMethodAdapterResolver` already takes, and for the same reason.

```php
interface ShippingRateProvider
{
    /** @return ShippingQuote[] — empty means this carrier will not carry it */
    public function quote(ShippingContext $context, CallBudget $budget): array;   // $budget: added in stage 3c, see §6.3
}

interface PickupPointProvider
{
    /** @return PickupPoint[] — offices and lockers for a settlement */
    public function pickupPointsIn(string $countryCode, string $settlement, CallBudget $budget): array;
}

interface ShipmentLabelProvider
{
    public function createLabel(ShipmentRequest $request): ShipmentLabel;
}
```

`ShippingContext` carries what any carrier needs and nothing a carrier should not see: the delivery address shape (country, settlement, whether it is a pickup point), the total weight in grams, the summed dimensions, the goods value for insurance and cash-on-delivery, and the currency. It carries **no customer identity and no cost prices.**

**A deliberate difference from `PaymentMethodAdapter`, worth stating because it is the one structural lesson from Shopify:** a payment is charged once, at the end, for a known amount. A shipping rate is needed **before the order exists**, several times, while the customer is still deciding. So `quote()` must be cheap, cacheable and failure-tolerant: a provider that times out must not take the checkout down with it. Shopify's own answer is caching identical requests and falling back to backup rates on a timeout; this design requires the same of whoever implements the first provider, and `checkout-orchestration-performance-note.md` §2's "never hold a DB transaction open across an external call" applies to `quote()` with full force.

**`PickupPointProvider` has nothing to change in `Address`** — it only *lists* what `Address` already knows how to store. That is why it is a small contract rather than a domain.

**`ShipmentLabelProvider` is the furthest away** and is named here only so the eventual Econt/Speedy work has a declared home. Nothing in V1 calls it.

### 6.1 What stage 3c built, and the decisions behind it

The contracts, the value objects (`ShippingContext`, `ShippingQuote`, `PickupPoint`, `ShipmentRequest`, `ShipmentLabel`, `CallBudget`) and the `CarrierRegistry` are in the Shipping package (`EasyCo\Shipping\Contracts`, `EasyCo\Shipping\Carrier`): plain PHP, no Laravel, no Hook, no import of another domain. Money is an integer in minor units plus an ISO 4217 code, as everywhere in this package. Every value object validates at construction (uppercase alpha-2 country, uppercase alpha-3 currency, no negative amount) and **refuses rather than normalizes**. The country check is a *shape* check, like `ShippingZone`'s: whether a code is a real country is the application boundary's job (`KnownCountryCode`). A validation message names the class and the field and **never repeats a value**, because these objects carry addresses and names and an exception message ends up in logs. The resolver, the guard and the registry's wiring are in `app/` (`ShippingProviderResolver`, `CarrierCallGuard`).

### 6.2 Resolver keys and the registry

A carrier's package binds each capability it offers as a **named container key**: `shipping.carrier.<code>.rate`, `shipping.carrier.<code>.pickup`, `shipping.carrier.<code>.label` (`CarrierCapability::containerKey()` writes the convention once). A carrier may bind only some. The same package registers **one entry** in the `CarrierRegistry` — code, display name, declared capabilities — from its service provider. **Core lists no carrier and ships none.** This replaces `PaymentMethodAdapterResolver::availableMethods()`' hand-written list, which cannot work for third parties; the container cannot be scanned instead because that would depend on keys core does not own.

`ShippingProviderResolver` refuses, **by name**, and **never falls back to a default or another carrier or another capability**: a code that is malformed or not registered (`UnknownShippingCarrierException` — a carrier that bound keys but never registered is unknown too, since an unlisted carrier must not be reachable); a registered carrier that does not offer the capability, declared it and bound nothing, or bound something that is not the contract (`CarrierCapabilityNotProvidedException`). A second registration of the same code is refused rather than replacing the first. A carrier code uses `ShippingCode`'s format, which has no dot, so a code can never reach another container key.

### 6.3 Failure semantics

Every rate and pickup-point call goes through `CarrierCallGuard`, which **never throws into checkout or the quote endpoint**. The result (`CarrierCallResult`) is either the provider's items — an empty list is an *answer* ("this carrier will not carry it"), not a failure — or `unavailable` with a reason from a closed list: `provider_error` (it threw, `Error`s included), `timed_out` (it answered after its budget; the answer is discarded), `invalid_response` (an item of the wrong type, a quote in another currency, a pickup point of another country or carrier), `not_configured` (unknown carrier or missing capability — the resolver's refusal, converted because the customer must not get a 500 for a merchant's configuration fault; it is logged with the carrier code). Each unavailability is logged at warning level with the carrier code, capability, reason, elapsed and budget milliseconds and the exception **class** — **never the context (it holds the destination) and never the exception message** (a provider may echo the address into it).

**The time budget is not enforced from outside, because PHP cannot interrupt arbitrary code.** It is passed to the provider as a `CallBudget`, and the contract **obliges every implementation to honour it** (typically as its HTTP client's timeout, connect and read together); the guard only measures and logs an overrun. Providers must also be side-effect free and must not hold a database transaction open (`checkout-orchestration-performance-note.md` §2).

**Label creation is deliberately not wrapped:** a failure there must surface to the merchant, and the idempotency reference below makes his retry safe. It also has no `CallBudget` parameter — a merchant waits for a label — though an implementation still sets a finite HTTP timeout of its own.

### 6.4 The label idempotency obligation

`ShipmentRequest` cannot be built without its **idempotency reference**: it is made from the order id and an attempt number (`"<orderId>#<attempt>"`, at most 64 characters), both required, the attempt at least 1. **Every `ShipmentLabelProvider` implementation is obliged** (stated in the contract's docblock) to make a retried request harmless: send the reference to the carrier as its client reference or idempotency key where the API accepts one; where it does not, look the shipment up by that reference before creating; a second call with the same reference returns the same label and never creates or charges again; if neither is possible the implementation must refuse to run rather than guess. A new attempt number is a **deliberate** new shipment (the first was cancelled or lost), chosen by the merchant's action and never by an automatic retry.

### 6.5 The quote cache (design only; built with the quote endpoint in stage 3d)

- **Key:** `shipping:quote:v1:<carrierCode>:<sha256 of the JSON of ShippingContext::toCanonicalArray()>` — the canonical array has a fixed key order and holds every field, so equal contexts share a key and any difference (settlement, weight, goods value, COD amount) is a different one. It holds no customer identity by construction. The `v1` is bumped when the context's shape changes.
- **Lifetime:** a successful answer, **10 minutes** (long enough to cover a customer deciding, short enough that a carrier's price change is picked up); an *unavailable* result, **30 seconds** (a failing carrier is not hammered by every keystroke, yet recovers quickly). An *empty* answer is cached like any other answer.
- **Never cached:** label creation; anything per order.
- **Where:** in the quote service of 3d, around `CarrierCallGuard`, in the application cache store; the guard itself stays cache-free.
- A merchant-level adjustment of quotes is an app-layer filter (`shipping.quotes`) applied by the quote service, not by the package; it is added with that service and gets its Hook Reference row in the same commit.

### 6.6 Proposals made in stage 3c (marked: §6 as written does not say these)

1. **`CallBudget` as a parameter of `quote()` and `pickupPointsIn()`.** §6's signatures had no way to pass the time budget the failure-tolerance paragraph requires. Built; the signatures above show it.
2. **`ShippingContext::$cashOnDeliveryMinor` (nullable).** §6 reuses the goods value "for insurance and cash-on-delivery", but they differ: a prepaid parcel is insured and collects nothing, and Bulgarian couriers price the cash-on-delivery service by the collected amount. Built; null means prepaid.
3. **Weight and dimensions are nullable, null meaning unknown, never zero.** A guessed zero would be priced as a weightless parcel. The three dimensions are all known or all unknown. §6's "summed dimensions" has no physical meaning for several items; the fields are the caller's best estimate of the parcel. Built.
4. **`ShipmentRequest` carries the recipient and the order id/attempt**, `ShippingContext` still none of it. Built.
5. **(Stage 3d part 1)** see §6.7 for the decisions taken there.
6. **NOT built, proposed for the first real carrier:** `postalCode` and `pickupPointReference` on `ShippingContext` (some couriers price by postcode or by the chosen office); `kind` (office or locker), opening hours and coordinates on `PickupPoint`; an estimated delivery time and a cash-on-delivery *fee* on `ShippingQuote`; the carrier's own cost and a cancel/track capability on `ShipmentLabel`. Each is additive and breaks nothing already built.

### 6.7 The quote service, the quote cache and the quote handle (stage 3d, part 1)

**The service** (`App\Services\ShippingQuoteService`) writes nothing to the database and opens no transaction; the only things it writes are cache entries (carrier answers and handles). The **caller resolves the cart server-side** — the service takes a `Cart`, never a client-supplied token — and gives either a destination (`QuoteDestination`: delivery type, country, settlement — a street address's city or a pickup point's settlement — and an optional postcode) or a saved `address_id` with the customer's account id; a saved address is read through `AddressResolver::resolveExisting()`, so "belongs to this account" and "has a country" are the one existing rule. Steps: `CartPricing` in preview mode (an unpriced line is skipped, as the cart does, and does not count toward the threshold) for goods after discount; the lines' shipping classes and weights in one `VariationRepository::findByIds`; the normalizer of the store's locale; `ZoneMatcher`; `ShippingRateCalculator` for the local methods; `CARRIER` methods through `CarrierQuoteCache` → `CarrierCallGuard` with an explicit budget (`QuoteCachePolicy::CARRIER_BUDGET_MS`, 3000 ms, handed to the provider). The result is, per **active** method of the matched zone: method id, name, kind, `requiresPickupPoint`, and either an amount or "unavailable" with a reason. **A carrier problem never throws**: that method is unavailable and the local methods still answer. Reasons: `provider_error`, `timed_out`, `invalid_response`, `not_configured` (the guard's), plus `no_quote` (the carrier answered and offers nothing for this parcel) and `no_settlement` (a carrier cannot quote a destination with no settlement).

**Refusals** are `ShippingQuoteRefusedException`s with a machine-readable `reason`, for the HTTP layer to map: `empty_cart`; `no_priced_lines` (the cart has lines but none has a price — added in 3d, not in the brief); `no_zone_for_destination`; `address_incomplete` (a saved address with no country); `address_not_found` (unknown **or** another account's address, indistinguishable on purpose; the HTTP layer maps it to 404).

**Two steps, on purpose.** `offers()` builds the complete priced list (`QuoteOffers`); `issueHandles()` then issues a handle for each method that has a price. The part-2 merchant filter (`shipping.quotes`) goes between them, so a handle is never issued for a price the filter then changed. `quote()` is the two in a row.

**A CARRIER method names a carrier, not a service** (§5), while a provider may return several quotes; the service takes the carrier's **cheapest** quote and reports its `serviceCode`. Which service a customer should get is the first real carrier's decision. Cash on delivery and dimensions are not passed to carriers yet (the collected amount depends on the very shipping price being asked for; "summed dimensions" has no meaning for several items — §6.6); the parcel weight is the sum over the priced lines and is **unknown (null) if any priced line has no weight**, never a partial sum.

**The cache** (`CarrierQuoteCache`, built as §6.5 designed): key `shipping:quote:v1:<carrier>:<sha256 of the canonical context>`; an answer (empty included) for 10 minutes, an unavailable result for 30 seconds (`QuoteCachePolicy`). Entries are plain arrays, never objects. **A cache that is down never takes a quote down:** a failed read or write is logged (exception class only) and the carrier is asked.

**The handle** (`QuoteHandleStore`): every method that has a price gets an opaque handle (`qh_` + 40 random characters), stored in the cache for **10 minutes** (`HANDLE_TTL`), keyed by a hash of the token (the secret is never a cache key), and bound to: the **cart id**, the **method id**, the **amount and currency**, and the **pricing hash** — a sha256 of everything that priced the quote: the destination as normalized (country, the settlement through the store's normalizer, the postcode through `PostcodeNormalizer` and ignored for a pickup point exactly as `ZoneMatcher` reads them, pickup or not), the matched zone, goods after discount and currency, every cart line with its quantity in a fixed order, and the promotion code (`ShippingQuoteService::pricingHashFor()`; checkout recomputes it the same way). An unavailable method gets no handle. **`verify()` accepts only a handle that exists, has not expired and matches the same cart, method, amount, currency and pricing hash**; anything else — unknown, expired (checked both by the cache's lifetime and against the expiry stored in the entry), another cart, a changed hash, a changed amount, a cache that cannot be read — is simply `false`. It does not consume the handle (a retried checkout may verify it again); whether placement consumes it is stage 4's decision. **What stage 4 verifies:** the client sends the handle with its chosen method; checkout recomputes the amount and the pricing hash server-side from the cart and the address it is about to place, and refuses the order (writing nothing, §9) unless `verify()` accepts the handle for exactly that cart, method, amount and hash. Checkout does not use it yet.

### 6.8 The public quote endpoint, the rate limiter and the `shipping.quotes` hook (stage 3d, part 2)

**Endpoint: `POST /api/shipping/quote`** (`ShippingQuoteController`). Public, outside the staff group like `/cart` and `/checkout`, so guests work (the route-table audit lists it as a storefront route). **The cart is resolved server-side exactly as `GET /cart` does** — the signed-in customer's own cart, else the guest session's cart; no cart is an empty cart; a `cart_id` or `cart_token` in the body is never read.

- **Request:** `delivery_type` (`street_address` | `pickup_point`), `country` (trimmed, uppercased by `KnownCountryCode::normalize()`, then checked by `KnownCountryCode`), `settlement` (required, trimmed — a street address's city, or the pickup point's settlement), `postal_code` (optional, ignored for a pickup point; named as in the checkout and address APIs) — **or** `address_id` alone, one of the customer's saved addresses (customer session only; a guest sending one gets a 422 on `address_id`; scoped to the account).
- **A pickup-point delivery is quoted from the settlement the client sends. The client must quote again after the customer chooses a point**, because the point's settlement may fall in another zone, with other methods and other prices; a handle belongs to the quote it came with.
- **200:** `cart_id`, `currency`, `goods_after_discount {minor, currency}`, `zone {id, name}` and `methods[]`, each with `id`, `name`, `kind`, `requires_pickup_point`, `available`, `price {minor, currency}` and `handle` (priced methods) or `unavailable_reason` (`provider_error`, `timed_out`, `invalid_response`, `not_configured`, `no_quote`, `no_settlement`), and `service_code` for a carrier method. The pricing hash is not exposed: checkout recomputes it.
- **Errors**, all `{message, reason}`: 422 `empty_cart`, `no_priced_lines`, `no_zone_for_destination`, `address_incomplete`; 404 `address_not_found` (an unknown address and another account's are the same answer); 422 with Laravel's own validation shape for a bad request; 429 `too_many_requests`; 500 `quote_filter_invalid` (a merchant's filter broke its contract, logged with the closed reason — per the Hook error policy a faulty listener is never papered over).
- **Messages are translated in the store's locale**, set explicitly from `StoreLocale::current()` for the request (and restored after), because the `api` middleware group never applies it (`lang/*/shipping_quote.php`; validation and country messages follow the same locale).

**Rate limiting — the convention.** All named API limiters are defined in ONE place, `App\Http\ApiRateLimits::register()` (called from `AppServiceProvider::boot()`); a route attaches one with `throttle:<name>`; the budget (requests per minute) is in `config/ratelimits.php` (`RATE_LIMIT_SHIPPING_QUOTE`, default 30). The key is "who asks, about what": the client IP plus the cart identity (the customer's id, else a **hash** of the guest cart token — never the token itself), so one shopper cannot exhaust everyone behind an IP and one IP cannot hammer many carts under one limit. A refusal is a 429 `{message, reason: "too_many_requests"}` with `Retry-After`, the message in the store locale. **The checkout endpoints reuse this** by adding a named limiter beside `shipping-quote`; the login route's inline `throttle:6,1` predates it and is untouched.

**The hook `shipping.quotes`** (a filter, `Hook::apply` in `ShippingQuoteService::applyQuotesFilter()`) runs on the method list **between building it and issuing handles**, so every handle binds the final amount. Signature `(list<MethodQuote> $methods, array $context): list<MethodQuote>`; the context holds the cart id, currency, goods after discount, zone id, destination country and settlement and whether it is a pickup point — **no customer identity**. **What a filter MAY do:** remove a method; change a method's amount (not below 0); return the methods in any order (the original order is kept, as it decides the preselection). **What it may NOT do — refused by name with `ShippingQuoteFilterException`:** add a method that is not an active method of the matched zone (`unknown_method`); return anything but a list of methods (`not_a_list`, `invalid_item`); repeat a method (`duplicate_method`); set an amount below 0 (`negative_amount`); turn an unavailable method into a priced one or the reverse (`availability_changed` — to hide a method, remove it); change anything else about a method, its name, kind, currency, carrier service or unavailable reason, or attach a handle (`changed_field`). With no listener the list passes through untouched. Listed in the Hook Reference of `extensibility-design-and-hooks.md` §3.

**The handle also binds the carrier service (review of part 1).** `QuoteHandleStore::issue()` and `verify()` take the quoted `serviceCode` (null for a local method) and `verify()` accepts only the same one, so checkout books exactly the service that was quoted. What stage 4 must do with it is recorded in `shipping-and-checkout-queue-note.md`.

## 7. `Order` finally carries shipping

```
Order
├── subtotalMinor
├── discountMinor
├── shippingMinor          NEW — what was charged for delivery, snapshotted
├── totalMinor             NOW subtotal - discount + shipping
├── shippingMethodName     NEW — snapshot of the method's name as shown
└── shippingMethodCode     NEW — nullable, which method was chosen
```

**This is the breaking part of the whole document and it has to happen before real orders exist.** `Order::create()` today computes `total = subtotal - discount` and deliberately refuses a separately supplied total, precisely so the two can never disagree. That refusal stays; the formula gains a term. Everything downstream that asserts the old formula — the checkout orchestrator, the order editor's re-planning, the payment reissue that compares a pending payment's amount against the order total, the admin panel's totals — must be found and updated together, not discovered one at a time.

**The method name is snapshotted, not referenced**, the same rule the address snapshot already follows: a merchant renaming "Еконт до офис" next year must not rewrite what last year's orders say they were charged for.

**An edit that changes the goods does not re-price shipping in V1.** The merchant adjusts it deliberately if he wants to — consistent with §3.1's "he edits the placed order", and with the existing rule that an edit never re-prices goods either. Automatic re-quoting on edit is deferred (§10).

### 7.1 Decisions taken for stage 2 (owner, final)

- **Shipping is an order-level amount only.** There is NO `SaleLine` for shipping: `SaleLineType::SHIPPING` exists in the enum and stays unused. The ledger therefore stays goods-only, and the placement reconciliation (`CheckoutOrchestrator::assertSaleLinesReconcileWithOrder`) keeps comparing the sum of the lines' `netPaidAmount` to `subtotal - discount` — **not** to the order total, which now also holds shipping.
- **`Order::reviseTotals` no longer accepts a total.** Its signature is `reviseTotals($subtotal, $discount, $appliedPromotionCode)`; it computes `total = subtotal - discount + (the order's stored shipping)` itself. This extends `Order::create()`'s existing rule — a total is never supplied by a caller — to the editing path, and it is how an edit carries shipping through unchanged. `OrderEditor` compares and reissues the pending payment against the order's resulting total (shipping included), while its goods reconciliation stays goods-only.
- **Name and code are nullable.** `shippingMethodName` and `shippingMethodCode` are null on an order with no shipping method (every order placed before this stage). Invariants: `shippingMinor` is never negative and is in the order's currency; a name, when given, is trimmed, non-empty and at most 255 characters; a code, when given, is trimmed, at most 64 characters and requires a name; `shippingMinor > 0` requires a name. The `Order` package does not import the Shipping package — name and code are plain strings.
- **Storage.** `orders.shipping_minor` (`bigInteger NOT NULL DEFAULT 0`), `shipping_method_name` (`string(255) NULL`), `shipping_method_code` (`string(64) NULL`). On MySQL/MariaDB the database also enforces `total_minor = subtotal_minor - discount_minor + shipping_minor` through a CHECK constraint (`orders_total_formula_check`), per CLAUDE.md rule 2.
- **Placement snapshots carry shipping in a LATER stage**, not stage 2. `order_placement_snapshots` is a write-once copy of the order at placement; adding the shipping fields to it belongs with the checkout integration (stage 4), which is the first writer of a non-zero value.

### 7.2 Refunds: the merchant decides every amount; EasyCo keeps the records, the caps and the facts

**Owner decision (final), replacing the earlier "refund policy behind one seam":** EasyCo hard-codes **no refund rule and no platform default**. Not "goods only", not "shipping on a cancel", not a return window, not a payment-method rule. Every refund amount is the merchant's decision, entered per refund. What EasyCo owns is the part that must never depend on a person's judgement: **correct records, hard caps, safe execution, and showing the facts the merchant's own policy depends on.** (The earlier version of this section, a table of the shop's own situations behind a "policy seam", is superseded. The shop's policy is the merchant's to apply by typing the amounts; it is not code.)

The points below that differ from the code as it stands are marked **(changes today's behaviour)**.

#### 7.2.1 The refund form, and what the ledger records

The cancel and return dialog collects one refund as these amounts:

| Field | Prefill | Editable |
|---|---|---|
| **Goods**, per line | the returned lines' net paid share, as today (`cumulative(r + k) − cumulative(r)` of `netPaidAmount`) | yes, per line — except on a pending payment (§7.2.4) |
| **Shipping refund** | 0 | yes |
| **Deduction** (optional) | 0 | yes — and a deduction **requires a free-text reason** |

`total = goods + shipping refund − deduction`. When the shipping refund is 0 the dialog shows a **neutral notice** stating the order's shipping amount (and how much of it has already been refunded); it never adds the shipping on its own and never suggests it. **(changes today's behaviour: the goods amount is no longer the only amount, and is no longer a value the caller cannot override.)**

**The ledger records what the merchant entered.** Each REFUND `SaleLine` stores the **merchant-ENTERED goods amount of that line** as its `amount` AND its `actualRefundAmount` (both, so a report summing either is true to the money; see §7.2.13), and the **computed share** as its `defaultRefundAmount` — the two facts `operational-sales-domain-design.md` §3.13 already defines for exactly this. **(changes today's behaviour: the lifecycle sets both to the computed share and exposes no override.)** The point is that product-level reports (what was refunded on this product, and for how much) stay true to the money that actually went back, not to a formula nobody applied.

**The deduction never touches a SaleLine.** It is a refund-level figure and lives **on the refund record**, with its reason. It is **retained revenue** — money the merchant keeps from the customer's payment — and is not a goods figure: it is not subtracted from any line, it appears in no product report, and the REFUND lines of the same return add up to the goods component only.

#### 7.2.2 Hard caps, cumulative across all refunds of the order

These are checked on every refund, against everything refunded before it. A refund counts toward a cap while it is **OWED, PAID_OUT, REQUESTED or COMPLETED**; a FAILED or CANCELLED refund (§7.2.11) moved no money and counts for nothing.

0. **Per line:** `goods refunded on this line so far + this line's goods refund ≤ that line's net paid amount`. A line can never be refunded more than the customer paid for it, however many partial returns it is spread over.
1. **Shipping:** `shipping refunded so far + this shipping refund ≤ the order's shipping`.
2. **Deduction:** `deduction ≤ goods + shipping refund (+ adjustment, §7.2.11)` of this refund — the refund total is never negative.
3. **Paid:** `total refunded so far + this total ≤ the amount actually paid` — the payment's received amount where one is recorded (§7.2.7), otherwise its expected amount. **(changes today's behaviour: the cap sums only COMPLETED refunds, so an in-flight refund is not counted; it must count every refund listed above.)**

A refund that breaks any cap is refused with a sentence naming the cap and the remaining room; nothing is written.

**What the refund record stores.** Every refund stores its **breakdown** as plain integers in minor units: goods (and, per line, the goods amount of each line — the rows the per-line cap sums, so that cancelling a refund frees exactly its own room), shipping, adjustment (§7.2.11), deduction with its reason, and the total, with `total = goods + shipping + adjustment − deduction`. On MySQL/MariaDB the database enforces it (CLAUDE.md rule 2): **CHECK constraints that every breakdown component is ≥ 0, that the total is ≥ 0, and that the total equals that sum.** The caps are aggregate rules across rows and cannot be a CHECK; they are enforced under the lock in §7.2.3.

#### 7.2.3 Concurrency, double submit, idempotency

- **One serialization point.** Every operation that moves money for an order already starts by locking the order row (`findByIdForUpdate`); the cap checks, the refund write, the void and the reissue all happen inside that one locked transaction, and nothing else may be added that checks a cap outside it. The payment-row lock that older text mentions is not what serializes today (the order lock is); the model keeps the order lock as the single point and states it.
- **Idempotency of the refund operation.** The dialog generates an **operation key** when it is opened and submits it with the form. The key is stored with a UNIQUE constraint — on the order's history row for the operation, so that an operation that writes **no** refund (a full cancel of a pending payment, §7.2.4) is covered too — and a second submission with the same key returns the first result and writes nothing. **(changes today's behaviour: there is no key. A cancel is protected only by the status guard, and a `recordReturn` submitted twice returns the units twice as long as enough remain.)**
- **Every state-changing action is idempotent.** "Mark as received", "mark paid out", "cancel an owed refund" and "mark remitted" (§7.2.7) are each a **no-op when repeated**: a second identical request changes nothing and writes **no second history entry**, whether it comes from a double click or a retry. Each is a conditional update inside the order-locked transaction (it applies only from the state it is defined for), not a read-then-write outside it.
- **No external call inside the transaction.** An offline refund calls nothing external. An online provider refund (§7.2.5) is never executed inside the database transaction: the transaction records it as REQUESTED and commits; the provider call happens after, and its result updates the record. **(today's `OrderRefunder` calls the adapter's `refund()` inside the open transaction; harmless for the two offline adapters, which call nothing, and not acceptable for an online one.)**

#### 7.2.4 Pending versus settled payments (this closes H1 and H2)

(H1 and H2 are the two defects found while preparing stage 2: H1, a cancelled order left with a new pending payment for its shipping amount; H2, a cancelled order whose paid shipping stays held without anyone deciding it.)

- **Pending payment: nothing is paid back, because nothing was paid.** A **full cancel or full return voids the pending payment completely and never issues a new one.** A **partial return** voids it and issues a new pending payment for the remainder: `pending amount − goods reduction − shipping reduction`. **The goods reduction is NOT editable on a pending payment: it is exactly the returned lines' share** (the dialog shows the per-line amounts read-only), because what the customer still owes for goods that were kept is not a negotiation on an unpaid order. **Only the shipping reduction is editable** (it may reduce what the customer still owes for delivery). A **deduction stays refused** on a pending payment (there is no money to deduct from). **(changes today's behaviour: today the remainder, shipping included, is reissued even on a full cancel, leaving a pending payment for the shipping amount on a CANCELLED order — H1.)**
- **Settled payment: a refund record is created** as §7.2.1–§7.2.2 describe, and the shipping that was paid is no longer silently left held, because the merchant now sees it and decides (H2).

#### 7.2.5 Refund states

One record, `PaymentRefund`, carries every kind, extended with the breakdown (§7.2.2), the operation key (§7.2.3), the payout channel (§7.2.8) and a state:

| Method | States |
|---|---|
| Offline (cash on delivery, bank transfer) | **OWED** — created by the cancel or return, dated; then **PAID_OUT** — the merchant confirms after paying in his bank app (or from the register): **date, reference, optional note**, and who. An OWED refund may instead be **CANCELLED** before payout (§7.2.11). |
| Online (a future provider) | **REQUESTED**, then **COMPLETED** or **FAILED**. Never executed inside a database transaction (§7.2.3). A FAILED refund frees its cap room. |

**(changes today's behaviour: an offline refund is recorded COMPLETED the moment it is created, which claims the money has been paid out when the system only knows it is owed.)** **Decided (owner, 2026-10-02): existing offline refund rows become PAID_OUT** with `paid_out_at` = their `created_at` and the note **"legacy: recorded before the owed/paid model"** (done by the migration that introduces the states, R1). Existing PENDING rows (online, none exist) become REQUESTED.

The order shows, from its refund records, four figures: **paid in**, **refunded and paid out**, **refunded but still owed**, and **still refundable** (paid in minus all counting refunds). **As built (R2b, §7.2.17):** *paid in* is the amount of the order's settled payment (0 when none has settled); *refunded and paid out* is the total of the PAID_OUT refunds (legacy ones included); *refunded but still owed* is the total of the OWED refunds; *still refundable* is paid in minus the total of ALL counting refunds (OWED, PAID_OUT, REQUESTED, COMPLETED). A cancelled or failed refund appears in none of them. The payout is recorded as a free-text reference; **no customer bank account number is stored in V1** (§7.2.10).

#### 7.2.6 Facts, not rules

The dialog and the order show the facts a shop's own policy depends on, and enforce none of them: the **delivery date** (the order's `delivered` history entry), the **day the customer announced the return** (a calendar day in the store timezone, entered by staff), the **date the goods came back** (entered by staff; the REFUND lines' `effectiveAt`, which today equals `recordedAt`), and the **days elapsed** between them. **Decided (owner, 2026-10-02): the announced-return date lives on the return operation's history row** (the `returned` event the operation writes), not on the refund record, because a return that produces no refund still has one. EasyCo enforces **no deadline**. A **filter hook** may later *suggest* prefill values from a shop's own policy; **EasyCo ships none**, and a suggestion is only ever a prefill the merchant can overwrite (the hook is app-layer, never called from a domain package — CLAUDE.md rule 10 — and gets its row in the Hook Reference when it is built). Money that is waiting on the merchant is listed under "Needs attention" (§7.2.7), which also enforces nothing.

#### 7.2.7 Payment verification, remittance, and "needs attention"

- **Bank transfer, "mark as received":** today it writes only `confirmed_at`. It stores, instead, the **received amount, the date and the bank reference** (and the staff member). If the received amount **differs from the expected amount**, the payment is **not settled silently**: the facts are recorded and the order is flagged **"needs attention"** until a person resolves it (accept the received amount, with a reason, which settles it for exactly that amount; or leave it unsettled). Refund caps (§7.2.2) then use the received amount.
  **R4a design (§7.2.20) — where the real code corrects this paragraph.** (1) "Stores, instead, the received amount, the date and the bank reference" cannot be columns on `payments`: `confirmed_at` is write-once and a payment can be unsettled **with** money in hand (order-lifecycle-design.md §4.5, §11 item 6), and a transfer can arrive in two parts — so the facts live in an **append-only `payment_receipts` table**, and only the *accepted* amount sits on the payment. (2) A mismatch that "leaves the payment unsettled" leaves **money in hand on a payment that a cancel, a return or an order edit would VOID** (`OrderRefunder` voids any pending, answered, unconfirmed payment; `PendingPaymentReissuer::currentPending()` has the same filter): the document did not say so, and R4a refuses those three operations while a receipt is unreconciled. (3) The refund cap base is read in **three** places, not the one §7.2.2 names (§7.2.20 §3). (4) "Mark as received" is offered for **every** confirmable payment today, cash on delivery included; R4a changes the bank-transfer path only, and cash on delivery stays exactly as it is until R4b.
- **Cash on delivery** has two facts that today are one. **Collected by the courier** — the cash was taken at the door — and **remitted to the merchant by the courier** — the courier's payout reaches the merchant's bank, usually days later. **Today "settled" for cash on delivery means neither exactly:** `deliver()` confirms any single eligible pending payment in the same transaction (`confirmDeliveryPaymentIfEligible`), so "settled" means "the order was marked delivered", i.e. collected, assumed. **Target:** keep that as **collected** (it is what unlocks refunds and reports), and add **remitted** as its own recorded fact.
- **Remittance is recorded per order as four facts:** the **remitted amount**, the **courier fee** (couriers usually remit in batches and may deduct a COD fee), the **date**, and the **bank reference**. A **batch action** marks **many orders remitted in one go with one shared reference**, each order keeping its own amount and fee. **The mismatch test is `collected − fee ≠ remitted`** — not `collected ≠ remitted`, which would flag every order that carries a fee. A mismatch is a "needs attention" item, not a block.
- **"Needs attention" lists facts and enforces nothing.** It shows, each with its **age in days** and **no threshold**: **OWED refunds** (days since created, oldest first), **payments with a received-amount mismatch**, **COD orders collected but not yet remitted** (days since collected), and **remittance mismatches**. Nothing is overdue by rule; the merchant reads the age and decides.

#### 7.2.8 Permissions and audit

- **The permission follows the PAYOUT CHANNEL. Decided (owner, 2026-10-02).** The merchant chooses the channel **when the refund is recorded** — **cash from the register** or **bank** — and that choice decides the permission for **both recording the refund and marking it paid out**: cash → `REFUND_CASH`, bank → `REFUND_BANK` (Administrator-only, per `staff-access-domain-design.md` §3.1). This replaces today's rule, which derives the permission from the *payment* method (`REFUND_CASH` for cash on delivery, `REFUND_BANK` for everything else) and lets a Manager record the refund of a cash-on-delivery order that will in fact be paid by bank transfer. A refund on a pending payment (§7.2.4) moves no money and needs only `ORDER_MANAGE`. **(changes today's behaviour.)**
- **Everything else** needs `ORDER_MANAGE`: cancelling an owed refund needs the same permission as recording it (the channel's), so that whoever may create it may withdraw it and nobody can withdraw one they could not have created.
- **Audit.** Every refund and every state change goes into the order's history with its breakdown and the staff member: the existing `refunded` event gains a reference to the refund record (today it carries only the return's transaction id and no amount), and new history entries are added for "refund paid out", "refund cancelled" (with its reason), "payment received (amount, reference)", "remittance recorded" and "needs attention".

#### 7.2.9 Return shipping is unchanged

Who bears return shipping is an **informational store setting** shown to the customer before ordering. No return-shipping money moves through the system.

#### 7.2.10 Privacy

The customer's bank account number is **not stored** in V1. The payout reference is free text the merchant types (for example his own bank reference).

#### 7.2.11 Corrections

Built in R2 (cancelling an owed refund) and R3 (the money-only refund).

- **An OWED refund may be CANCELLED before payout.** The refund moves to **CANCELLED**, which **frees its cap room** (it no longer counts in §7.2.2, per line included), and writes **one history entry carrying the staff member and a mandatory reason**. A **PAID_OUT refund is never cancelled** — money that left cannot be un-recorded; a mistake after payout is corrected by a new refund or recorded outside the system. Cancelling a refund cancels the *money* only: the goods stay returned, stock stays restocked, and the REFUND `SaleLine`s are never edited or deleted (CLAUDE.md rule 4). Reports exclude a cancelled refund's goods amounts by a **compensating (storno) ledger line** appended in the same locked transaction as the cancellation (decided, §7.2.13, option (b)); a `SaleLine` is never rewritten.
- **PAID_OUT confirms exactly the owed total.** Marking a refund paid out records that **the owed total** was paid; **a different amount is not a payout but a correction**: cancel the owed refund and record a new one for the amount actually to be paid.
- **A money-only refund ("refund without return").** A refund with **goods 0**: a **shipping refund** and/or an **adjustment amount**, with a **mandatory free-text reason**. It runs under **the same caps** (§7.2.2, shipping and total; there is no goods line, so no per-line cap applies), **the same states** (§7.2.5), **the same idempotency** (§7.2.3) and the same permission by channel (§7.2.8). It covers **goodwill and corrections** and **touches no stock and no `SaleLine`**; the adjustment is a refund-level component stored on the refund record like the deduction, never a goods figure. (An adjustment is available only on a money-only refund; a return's refund uses the goods lines.)

#### 7.2.12 Staged implementation plan

Each stage ends in a review gate. **R1 must land before shipping stage 4** (checkout), so no non-zero-shipping order can exist without the pending-payment rules and the caps; R2–R4 follow shipping stage 3d; R5 comes with the first online payment method.

**R1 — The refund record, the caps, the lock, the idempotency, the pending rules, the state set.** `PaymentRefund` gains the breakdown (goods, per-line goods rows, shipping, adjustment, deduction and reason, total), the operation key (UNIQUE), the payout channel and the state set (OWED, PAID_OUT, CANCELLED, REQUESTED, COMPLETED, FAILED); the CHECKs of §7.2.2; the migration that maps existing rows (§7.2.5); cap checks under the order lock counting every counting refund, including the per-line cap; the REFUND lines record the entered amount; the pending-payment rules, including the read-only goods reduction. No dialog change beyond passing the key and the prefilled amounts.
Tests: a **cumulative cap across two partial returns** (shipping and total); a **per-line cap** (two partial returns of one line can never exceed its net paid amount); the **ledger records the entered amount** (the REFUND line's `actualRefundAmount` is the entered amount and `defaultRefundAmount` the computed share, and the deduction appears on no line); a **double submit creates one refund** (and one return); **concurrent refunds cannot exceed the paid amount** (two transactions racing the same order); a **full cancel on a pending payment never reissues**; a **deduction on a pending payment is refused**; the **goods reduction on a pending payment is not editable** (a submitted goods amount other than the returned lines' share is refused) while the shipping reduction is; a partial return on a pending payment reissues exactly `pending − goods − shipping`; a deduction larger than goods + shipping is refused; a FAILED refund frees its cap room; the CHECKs reject a negative component and an inconsistent total; the mapping migration turns an existing offline refund into PAID_OUT with the legacy note.

#### 7.2.13 Decisions taken for R1a (owner, final)

1. **The ledger is the source of truth for money refunded per product line (option (b)).** A cancelled OWED refund will append a **storno `SaleLine`** (built in R2, not R1a); a corrected refund appends a new money line, never rewrites one. Reasons, from the code: `OperationalSales` may not read `payment_refunds` (it depends on Pricing only, CLAUDE.md rule 9), so a ledger report cannot join refund rows; POS register refunds are immediate cash with no refund record, so the ledger is the only record both channels share; and CLAUDE.md rule 4 already says a correction is a new row. The refund record's per-line rows (`payment_refund_lines`) are **operational state**: they drive the caps and the cancellation. R2 adds a test that, per line, non-cancelled refund rows equal REFUND minus storno lines.
2. **A REFUND `SaleLine`'s `amount` AND `actualRefundAmount` hold the merchant-ENTERED amount; `defaultRefundAmount` keeps the computed share.** A REFUND line may carry **0** (the goods came back, no money is paid for that line). `SaleLine::createRefund()` takes the entered amount as an optional argument (non-negative, in the origin's currency). The computed share keeps its own stricter positive-only guard, unchanged.
3. **A refund whose total would be 0 creates no `PaymentRefund`** (the domain's `amount > 0` stays). The goods still move: the REFUND lines are written, stock is restocked, a `returned` event is recorded, and no refund event is.
4. **Idempotency (built in R1b):** a repeat with the same operation key and the **same payload** returns the first result; the same key with a **different payload** is refused with a clear, translated error. A payload hash is stored next to the key.
5. **The money permission follows the payout channel and is enforced in the service layer as well as in the UI** (built in R1b). Until then it is the existing UI-only check, now reading the stored channel.
6. **Concurrency testing (R1b):** the deterministic two-connection lock test is required; a subprocess race test is optional and only if it is fully deterministic.

**What R1a built.** `payment_refunds` carries the order link, the payout channel, the breakdown (`goods_minor`, `shipping_minor`, `adjustment_minor`, `deduction_minor` + its reason; `amount_minor` stays the total) and the paid-out facts; `payment_refund_lines` holds the per-line goods rows (real FKs to the refund and to the original SALE line, UNIQUE per pair). The states are OWED, PAID_OUT, CANCELLED, REQUESTED, COMPLETED, FAILED. CHECKs (MySQL/MariaDB only): every part ≥ 0, total ≥ 0 and = goods + shipping + adjustment − deduction, a deduction requires its reason, a line amount ≥ 0. Existing offline refunds were mapped to PAID_OUT with the note "legacy: recorded before the owed/paid model" (a gate refuses a refund with no payment, or a COMPLETED one on a non-offline method, rather than guess). Both offline adapters now return OWED; `PaymentMethodAdapter::isOffline()` exists and the refund path refuses any adapter that is not offline, by name — an online refund never runs inside the order-locked transaction (R5). The payment cap counts every refund whose money is spoken for (OWED, PAID_OUT, REQUESTED, COMPLETED). The order history shows an OWED refund as **"refund owed"** (`refund_owed`), not "refunded". `OrderStatusChanger::cancel()` / `recordReturn()` take an optional `RefundRequest` whose defaults are exactly today's dialog (computed shares, shipping 0, deduction 0, channel derived: cash on delivery → cash, otherwise bank); non-default values are reachable only from tests until R1b adds the caps and R3 the dialog.

#### 7.2.14 What R1b built, and the decisions behind it (owner, final)

- **The caps are live** (`RefundCapGuard`, called from `OrderRefunder`, inside the order-locked transaction and before any refund write): per original sale line, shipping, total against the settled payment, and the deduction against the goods + shipping of the same refund. CANCELLED and FAILED refunds free their room, per line included. A broken cap throws `RefundCapExceededException`, a translated sentence naming the cap and the room left (`orders.refund_caps.*`, en + bg); the whole transaction — goods lines and restock included — rolls back, and the admin action shows it as a refusal notice, never a 500.
- **Legacy refunds get their per-line rows before the per-line cap goes live** (migration `2026_10_06_000002_backfill_payment_refund_lines`). A refund written before R1a has no `payment_refund_lines`, so the cap would have believed its line had never been refunded. The rows are rebuilt from the REFUND sale lines of the return that produced the refund, through the link that really exists: the `returned` and `refunded` events of the return carry the return's `transaction_id`, and a refund carries only a payment id (which gives its order). So, per order, its goods-bearing refunds without lines are paired in id order with its `refunded` events; the pairing is accepted only if it is unambiguous (equal counts) and each pair's REFUND lines add up to the refund's goods. **It is a gate:** otherwise it writes nothing and aborts naming the refund ids. A refund with goods 0 needs no lines.
- **A fully discounted line is returnable.** `defaultRefundAmount` (the computed share) must be positive, except that exactly 0 is accepted when the line has no net paid left to give back (`net paid − cumulative(already returned)` is 0: a gift, a 100% discount). The goods move and restock; no money does, and if every line of the return is free no refund exists (decision 3). A negative share is always refused. **(Superseded in R1c, §7.2.15: a computed share of 0 is legal whenever it is not negative, whether or not net paid remains.)**
- **Idempotency** (`order_events.operation_key`, `operation_payload_hash`, `payment_refund_id`; UNIQUE (`order_id`, `operation_key`), CHECK key and hash together). The key is on the **first** event the operation writes. Under the order lock, **before** the status guard (a finished cancel has moved the order to a status that guard would refuse), a repeat of the same key with the same hash returns the first result (`OrderReturnResult::wasReplay()`, with the first refund) and writes nothing and fires no hook; the same key with a **different** hash throws `OperationKeyReusedException`, translated (en, bg). **The hash (sha256) covers everything the merchant decided:** the action (cancel or return), the lines with quantities and restock choice, a cancel's restock overrides, the entered goods amounts, the shipping refund, the deduction and its reason, the channel, and the operation's free-text reason; every map is sorted first, so the order a form submitted things in is irrelevant. The unique index is only the backstop (a duplicate-key error re-runs the call once and replays). The cancel/return dialog carries one hidden key generated when it opens.
- **The money permission is enforced in the service.** Recording a refund on a **settled** payment requires the permission of its payout channel — `REFUND_CASH` for cash, `REFUND_BANK` for bank — checked in `OrderRefunder` before the caps, for the acting panel staff member (`PanelStaffActor` + `AuthenticatedStaffResolver`, the pair the UI check already used). **No acting staff member is a refusal** (fail closed): an unattended path must not record a payout the panel would show to nobody. A refusal is `RefundPermissionDeniedException`, translated, shown as a notice. The panel's visibility clause and the service both read `RefundPermissionPolicy::permissionFor()` — one derivation, so they cannot disagree. A refund on a pending payment moves no money and needs only `ORDER_MANAGE`, which is still checked by the panel only.

#### 7.2.15 What R1c built, and the decisions behind it (owner, final)

- **The pending-payment rules of §7.2.4 are live** (`OrderRefunder::voidAndMaybeReissue()`; `OrderStatusChanger` passes it the full-return flag, `$allEmptied`, computed before the money step). A **full cancel or full return voids the pending payment and never reissues** — H1 is closed; this includes a full cancel whose returned goods were all free (total 0), which used to reach no money step at all and now still reaches the refunder so the payment is voided. A **partial return** voids it and reissues exactly `pending − goods − shipping reduction`; the reduction defaults to 0, which is the behaviour before R1c. On a pending payment a **deduction is refused** and an **entered goods amount different from the computed share is refused** (`PendingPaymentRefundRuleException`, translated en + bg, shown as a notice; entering exactly the computed share is no deviation); a **shipping reduction is accepted and capped** at the order's shipping not already reduced (`RefundCapExceededException::PENDING_SHIPPING`, room named). Nothing is refunded on a pending payment, so no refund record remembers earlier reductions: they are read off the pending payment itself, which every earlier partial return reissued for `previous − goods − reduction` — `reduced so far = order total − goods credited by earlier returns − pending amount` (orders cannot be edited once a return is possible, so only returns move those figures). A shipping reduction entered with a **full** cancel/return is moot (everything is voided) and is not checked.
- **H2 needs no new code:** a full cancel of a **settled** payment with an entered shipping refund records one refund of goods + shipping, the shipping capped at `orders.shipping_minor` (R1a built the parameter, R1b the cap); R1c adds the tests that say so.
- **A computed share of 0 is legal** (supersedes the R1b rule). The share is a cumulative rounding — `floor(net paid × n / quantity)` — so a 1-cent line of 3 units has shares 0, 0, 1, and every unit must be returnable. `SaleLine::createRefund()` now refuses only a **negative** computed share; the `originRemainingNetPaid` parameter R1b added is gone. A return whose lines all have a zero total records no refund (R1a decision 3), and the money across the three returns of that example totals exactly 1 cent.
- **The per-line cap is edit-aware, and needed no fix.** An edit made while the order is unpaid reverses the old line and writes a replacement line with its own net paid, and a cancellation or return can only name a **current** line (`OrderCurrentLinesResolver::resolveWithReturns()`, which excludes a line reversed away). So the cap, which reads the net paid of the line the return names, reads the replacement's — what was really paid after the edit — never the pre-edit amount. Tested end to end: a line edited 3 → 2 while pending, settled, then returned with an amount above the post-edit net paid is refused by the per-line cap with the post-edit room.
- **A non-staff caller cannot record a settled refund.** The money permission of §7.2.8 is checked against the acting panel staff member, and no acting staff member is a refusal (fail closed). So a console command, a queued job or a future courier webhook cannot record a refund on a settled payment. Such automation will need an **explicit system actor holding the permission**, designed when the first one exists; until then this is the intended behaviour, not a gap to patch around.

#### 7.2.16 What R2a built (service and domain layer; the screens are R2b)

- **OWED → PAID_OUT** (`RefundStatusChanger::markPaidOut()`, `PaymentRefund::markPaidOut()`). Inputs: the **payout date** (entered, never after the caller's clock), a **bank reference** (required for channel `bank`, optional for `cash`), an optional note, and the staff member. **The amount is not an input:** PAID_OUT confirms exactly the owed total. It runs in the **order-locked transaction**, checks **the permission of the refund's channel** (`REFUND_CASH` / `REFUND_BANK`, through the same `RefundPermissionPolicy`; no acting staff member is a refusal), and is **idempotent through the existing `operation_key`** (§7.2.3): the key and a payload hash go on the one `refund_paid_out` event; a repeat returns the first result, writes no second event and fires no hook; the same key with other contents is refused. Any state other than OWED is refused by name (`not_owed`); so are a future date (`payout_in_future`) and a bank payout with no reference (`bank_reference_required`) — all `RefundTransitionRefusedException`, translated en and bg.
- **OWED → CANCELLED** (`RefundStatusChanger::cancelOwed()`, `PaymentRefund::cancelOwed()`): a **mandatory reason** and the staff member, the same permission rule, lock and idempotency. When, why and by whom are stored on the refund (`cancelled_at`, `cancelled_reason`, `cancelled_by`, with a CHECK that they are set together and only on a CANCELLED row). **A PAID_OUT refund can never be cancelled**, a legacy refund (mapped to PAID_OUT) included. The refund's **room in every cap is freed by its state alone** (CANCELLED already does not count; tested by re-recording the same amount). **The goods stay returned and restocked**: no stock change and no change to a REFUND line.
- **The storno line.** A new SaleLine type `REFUND_REVERSAL`, modelled on `EDIT_REVERSAL` (`SaleLine::createRefundReversal()`, in both allow-lists). Cancelling an OWED refund appends, in the same transaction and in a Transaction of its own (which the `refund_cancelled` event points at), **one storno per refund line**: `amount` is that line's entered amount (positive, **zero when the line was entered as 0**), `quantity` the line's own, `quantityReturned` and the two refund amounts **null**, `originatingSaleLineId` **the REFUND line it reverses** (the SALE line is one hop further), the reason and the staff member in the return columns. The REFUND lines are found through the history, never guessed: the refund's own `refund_owed` event (which carries `payment_refund_id` since R1b) names the return Transaction that wrote them; if it does not (a refund recorded before R1b), or the recorded line amount disagrees with the ledger, the cancellation is refused by name (`refund_lines_unlinked`, `storno_mismatch`) and nothing is written. **Every quantity sum filters on `type = refund`, so a storno changes nothing about what counts as returned** (tested for the returned and the edited-away sums and for a further return). **The ledger rule:** for every product line, the sum of the non-cancelled refund lines equals the REFUND amounts minus the storno amounts (tested).
- **Hooks (replacing `order.refunded`).** `order.refunded` fired for a refund that was only OWED, so an extension could have told a customer that money was returned before it was. It is **removed** (no listener existed in the repository; only tests used it) and replaced by three, all after the commit and never for a replay or a refused call: **`order.refund_recorded`** — a refund record was created (OWED today; an online method may create it COMPLETED) — fired by `cancel()`/`recordReturn()`, also for a partial return; **`order.refund_paid_out`** — money actually left: OWED → PAID_OUT, or an online refund that is already COMPLETED (never for an OWED refund); **`order.refund_cancelled`** — an OWED refund was cancelled. The order's own terminal status (CANCELLED / REFUNDED) is announced by `order.status_changed` (and `order.cancelled`) as before. Hook Reference rows are in `extensibility-design-and-hooks.md` §3.
- **History:** two new order events, `refund_paid_out` and `refund_cancelled`, labelled in en and bg, each carrying the refund id; `refund_owed` keeps its label.
- **Fail loud in the pending shipping reduction:** the derived "reduced so far" (§7.2.15) below zero is a broken invariant, not "nothing reduced": `PendingShippingInvariantBrokenException` (a `LogicException` naming the order, the payment and the figure) replaces the silent clamp to 0.

#### 7.2.17 What R2b built (the admin screens)

- **The refunds section of the order page** (`OrderResource`, read by `OrderRefundsReader`; nothing at all for an order with no refund): the four figures of §7.2.5 and one block per refund, **newest first** — state badge (owed = warning, paid out = success, cancelled = danger, a legacy paid-out refund = quiet gray with its own label "Paid out (legacy)"), channel, the breakdown (goods, shipping, and adjustment / deduction with its reason only when non-zero), the total, and the facts: recorded (when, by whom, why), paid out (when, by whom, reference, note), cancelled (when, by whom, why). The reader works from raw rows, so a legacy refund (no staff, the mapped note — which is not shown) reads sensibly. **Open points of §7.2.5, reported not invented:** the document gives the fourth figure the name "still refundable", which is what the screen says; and the online states REQUESTED / COMPLETED have no home in the first two figures (none exists yet), so they count only in "still refundable", as the sentence defines it.
- **Mark paid out** and **Cancel refund** buttons on an OWED refund (`mark_refund_paid_out`, `cancel_refund`, in a per-refund actions block `refund_actions_<id>`). Paid out: the payout date (default now, not in the future), the bank reference (required for channel bank, optional for cash), an optional note; the amount is shown and cannot be edited. Cancel: a mandatory reason and the warning that the goods stay returned and only the money record is cancelled. Both send one **hidden operation key** generated when the dialog opens (§7.2.3). Both are visible **only while the refund is OWED** (read fresh, not from the page's snapshot) **and only to staff holding the permission of the refund's own channel**, through `RefundPermissionPolicy::permissionFor()` — the derivation the service enforces. #### 7.2.18 What R3 part 1 built (the service layer; the dialog is part 2)

- **The money-only refund** (`MoneyOnlyRefunder::record()`, request `MoneyOnlyRefundRequest`; the settled-payment work is `OrderRefunder::refundMoneyOnly()`, which reuses the settled-refund path unchanged). Goods 0: a shipping refund and/or an adjustment, a **mandatory reason**, a **payout channel**, an optional operation key. **No SaleLine, no stock movement, no status change**, one `PaymentRefund` (OWED for the offline methods; `adjustment_minor` carries the adjustment) and **one `refund_owed` history event** that carries the refund id (`transaction_id` is null: there is no return). **Refused by name** (`MoneyOnlyRefundRefusedException`, translated en + bg): `reason_required`; `payment_not_settled` — a pending payment, or none, because nothing was paid, and **it never voids or reissues anything**; `deduction_not_allowed`; `nothing_to_refund` (shipping + adjustment = 0). The same caps (shipping, total; no line, so no per-line cap), the same order lock, the same permission by payout channel (checked in the service, no acting staff member is a refusal), the same idempotency (key + payload hash on the `refund_owed` event, replay returns the first refund and writes and fires nothing, other contents are `OperationKeyReusedException`, the UNIQUE index is the backstop), `order.refund_recorded` after the commit. **No order status is required**: goodwill on a delivered or a cancelled order is the merchant's call, and the settled payment is the only guard. An OWED money-only refund can be cancelled like any other (`cancelOwed()`); it has no goods lines, so it appends no storno.
- **The announced-return day** (owner decision Q3, §7.2.6) is an optional `announcedReturnOn` on `RefundRequest`, read by **`recordReturn()` only** (`cancel()` refuses it with an `InvalidArgumentException`: a cancellation has no customer-announced return). **It is a CALENDAR DAY in the store's timezone, a plain `'Y-m-d'` string — not an instant** (corrected in R3 part 2: the merchant types a date, nobody types hours, and a date turned into a midnight instant shifts across the UTC boundary and breaks the placement check). `RefundRequest` refuses anything that is not a real `Y-m-d` date. It is validated under the order lock, after the key replay and the status check, before anything is written: with *placedDay* and *recordedDay* the store-timezone calendar days of the order's placement and of the recording moment, the announced day must satisfy **placedDay ≤ day ≤ recordedDay**, both inclusive; otherwise `ReturnAnnouncedDateException` (`in_future` / `before_placement`, translated). It is part of the operation's payload hash (only when given, so the hash of every operation without one is unchanged). **Storage: a nullable DATE column `order_events.announced_return_on`** on the `returned` row, **not** the event's payload, because `order_events` has no payload column and the order page already reads the whole history with one `select *`, so the column arrives with rows it reads anyway — no extra query, no join; and a column can carry a CHECK (MySQL/MariaDB: only a `returned` row may carry it, `oe_announced_return_check`) where a payload cannot (CLAUDE.md rule 2). **Part 1 stored a UTC timestamp `announced_return_at`; migration `2026_10_07_000002` replaced that column** (it was never filled in production; any dev value is converted to its store-timezone day, not truncated to the UTC day). `OrderEventModel` casts it `date:Y-m-d` with no timezone shift; `OrderEventRecorder` refuses it on any other event type. The store timezone is read in the service layer through **`App\Settings\StoreTimezone`** (next to `StoreLocale`; `site.timezone`, then `services.site.default_timezone`, then `app.timezone` — the very chain `ApplyStoreTimezone` feeds Filament, which now asks it too); `config('app.timezone')` stays UTC and storage stays UTC.
- **The return facts reader** (`OrderReturnFactsReader::forOrder()` → `OrderReturnFacts` + `OrderReturnFact`): ONE query over the order's `returned` events and its `delivered` status change. It reports the **delivery** (an instant), and per return its **recorded** moment (an instant), the **announced day** (a date, no time; null when nobody entered it) and the **calendar days** from the delivery day to each, plus `daysSinceDelivery($asOf)` for the order. **Every day count is the difference of two calendar days in the store timezone** (day of the later date minus day of the earlier one), which is what a shop's own "14 days" means — a delivery at 01:30 Sofia time and a return at 23:59 Sofia time 14 days later is 14, though it is 13 in 24-hour periods. A count is **negative** when the later date falls on an earlier day (a delivery recorded late): the sign is kept, never clamped, never an error. **Facts, not rules**: no deadline exists in it or in anything it feeds, and a return 398 days after the delivery is recorded and refunded like any other (tested). An order never delivered has no delivery date and no day counts; a cancellation also writes a `returned` event, so it appears in the list with no announced day.

Visible only with `ORDER_MANAGE`, a settled payment and at least one channel permission; no order status is required (delivered and cancelled orders too). It calls `MoneyOnlyRefunder::record()` with one operation key generated when the dialog opens.

Every service refusal — caps, permission, pending rules, key reuse, `MoneyOnlyRefundRefusedException`, `ReturnAnnouncedDateException` — is a translated notice, never a 500 (`runOrderAction`). #### 7.2.20 R4a design (bank-transfer receipt, mismatch resolution, "needs attention") — designed and DECIDED by the owner (2026-10-05), NOT built

*Status: the owner's decisions are recorded in §11 (2026-10-05); nothing here is built. Written against the code as it is on the day of this pass (2026-10-05). §7.2.7 and §7.2.2 stay the source of the rules; this section is where they meet the code. The numbering is §7.2.20, not the §7.2.19 an earlier plan suggested: R3 part 2 took §7.2.19.*

**1. What the code does today (reconnaissance, with the places).**

- **`confirmed_at` has exactly two writers**, both through `OrderPaymentConfirmer::confirmWithinOpenTransaction()` (`app/Services/OrderPaymentConfirmer.php:163`): the panel's `markAsReceivedAction()` (`OrderResource.php`, "mark_as_received", `ORDER_MANAGE`, visible while `latestPayment->isConfirmable()`) and cash on delivery's R10 inside `OrderStatusChanger::deliver()` (`confirmDeliveryPaymentIfEligible`, `OrderStatusChanger.php`). The action passes `new DateTimeImmutable` as the instant: `confirmed_at` is **when the merchant recorded it, not the day the money arrived**; nothing records an amount, a day, a reference. It writes one `payment_confirmed` event and fires `order.payment_confirmed (Payment)`.
- **"Settled" is one predicate**: `Payment::isSettled()` = `status = captured OR confirmed_at IS NOT NULL` (`Payment.php:299`). The database mirrors it with the stored generated column `settled_order_id` + `UNIQUE pay_settled_order_unique` — **at most one settled payment per order, enforced by the engine**. `confirm()` is one-time and there is deliberately no un-confirm (§4.5, §11 item 6 of order-lifecycle-design.md). `findSettledForOrder()` exists on the repository and **nothing calls it**.
- **The expected amount is `payments.amount_minor`**, set to `order->total()` when checkout writes the row (`CheckoutOrchestrator.php:~418`) and kept in step by void-and-reissue while the payment is pending: an edit (`OrderEditor`, only allowed while **no** payment is settled — E3) or a partial return on a pending payment voids the row and appends a new pending one for the new target (`PendingPaymentReissuer::reissueFor`). A settled payment's amount never changes; after settlement the order can be returned but not edited.
- **Who reads "settled"**: the refund caps (`RefundCapGuard::totalRoom`, which therefore also feeds `RefundFormReader`, `OrderRefunder`, `MoneyOnlyRefunder`), `OrderRefundsReader` (the "paid in" figure), `OrderStatusChanger::guardBankTransferSettled` (R9), `OrderEditor` (E3), `OrderRefunder::settledOf/pendingEligibleOf` (and so the dialogs), the order page (payment badge, `payment_confirmed_at` entry, money summary), `PendingPaymentReissuer`. **No report, no list filter, no API field and no other query reads `confirmed_at`** (the order list filters by payment *method* only; the checkout API returns the status only).
- **The cap base is `payment->amount()` in three places**: `RefundCapGuard::totalRoom()` (`RefundCapGuard.php:169-173`), `OrderRefundsReader.php:55` (paid in) and the "Paid" row of the money summary (`OrderResource.php` ~1115, `$payment->amount()->minorValue()`). The offline adapters' `refund()` ignore the amount. §7.2.2 names only the first.
- **R9 and the statuses**: a `confirmed → shipped` move is refused while a bank-transfer order has no settled payment; nothing else depends on a bank payment being settled — `placed → confirmed` and cancel are free, and `shipped → delivered` is free (it confirms *cash on delivery* in the same transaction, R10). So an unsettled (under- or over-paid) transfer **blocks shipping, and nothing else**, which is exactly what R4a wants; an order cannot reach `shipped`, and so not `delivered`, with an unsettled bank payment, which is why R4a needs no change to any status rule.
- **Nothing lists OWED refunds anywhere.** The only surface is the per-order refunds section (`OrderRefundsReader`, one query a page). `payment_refunds` has **no index on `status` or `created_at`** (only `payment_id` and the R1a ones). Admin conventions: a page is a `Page` with `AuthorizesViaStaffPermission`, a `NavigationGroup` case (`CATALOG`, `SALES`, `ADMIN`), a nav label and a mount-time `canAccess()` re-check (`ActivityLogJournal`); the panel registers Filament's default `Dashboard` with only the stock `AccountWidget` and `FilamentInfoWidget` (`AdminPanelProvider.php`), and `app/Filament/Widgets` does not exist.
- **Permissions**: `markAsReceived` needs `ORDER_MANAGE` (Administrator and Manager hold it; Product Entry does not); `REFUND_CASH` is held by Administrator and Manager, `REFUND_BANK` by Administrator only. **A new permission is a known recipe, not a free change**: enum case + the seeder list + a migration that adds it to the *existing* Administrator row (`seedIfMissing` never updates an existing role — see the product-delete and order-discount migrations and their tests) + the `lang/*/roles.php` label.
- **Legacy**: every existing confirmed bank-transfer payment has `confirmed_at` set and no amount, day or reference. Under R4a it is *settled, expected = received, nothing recorded*; no mismatch can ever be derived for it (a mismatch needs receipts on an unsettled payment) and **no receipt is invented for it**.
- **Hooks that exist**: `order.payment_confirmed (Payment)` (after commit; zero listeners). R4a adds three (§5).

**2. Persistence — DECIDED: a receipts table, and two columns on `payments` that only an *accepted mismatch* writes.**

*Why not columns on `payments` alone:* one row could hold one transfer, so a payment received in two parts, or a typo before settlement, would have to **mutate** facts on a row whose design is append-only (payment-domain-design.md §1) and whose `confirmed_at` is write-once. *Why a table:* it mirrors `payment_refunds`, keeps `confirm()` untouched as the single settlement fact, and gives the audit one row per observed transfer.

- **`payment_receipts`** (Payment package, new migration; append-only, no `updated_at`, no delete): `id`; `payment_id` (**real FK** to `payments.id`, restrict — unlike `payment_refunds.payment_id` there is no "is it captured" rule to keep out of the database; short name `prc_payment_fk`); `amount_minor` BIGINT + `amount_currency` CHAR(3) (CHECK `amount_minor > 0`; the currency must equal the payment's — service rule); `received_on` **DATE** (a calendar day in the store timezone — §0 of the standing rules); `bank_reference` VARCHAR(64) NOT NULL (CHECK non-blank on MySQL/MariaDB; 64 = a SEPA end-to-end id is at most 35, with headroom; **the form's `maxLength` is 64 too**); `supersedes_receipt_id` nullable self-FK (`prc_supersedes_fk`) with `UNIQUE prc_supersedes_unique` — a receipt is superseded at most once; `recorded_by` (the same shape as `payment_refunds.refunded_by`) and `recorded_at` TIMESTAMP (UTC instant). Index `prc_payment_idx (payment_id)`. A receipt is **effective** unless a later row names it in `supersedes_receipt_id`; the effective sum is `SUM(amount_minor)` over effective rows (one grouped read). At most **20 effective receipts per payment** (a service rule, so every sum stays far below `PHP_INT_MAX`: each amount is ≤ 9 integer digits through `MoneyInput`), and at most **50 rows per payment in total, superseded ones counted** (so a correction chain stays bounded: refusal by name `too_many_receipt_rows`, translated). The two limits are independent and both are checked under the order lock: the 20 bounds the rows that count in the sum, the 50 bounds the history; `record()` checks both (a 21st effective receipt, or a 51st row, is refused), `correct()` checks only the 50 (a correction replaces one effective receipt with another, so it never raises the effective count). A payment can reach 50 rows with far fewer than 20 effective ones.
- **`payments`** gains two nullable columns, written **only** by an accepted mismatch, in the same `confirm()`: `settled_amount_minor` BIGINT and `settlement_reason` VARCHAR(255). CHECKs (MySQL/MariaDB): both or neither; `settled_amount_minor > 0`; `settled_amount_minor <> amount_minor` (an acceptance exists only for a real difference); `settled_amount_minor IS NULL OR confirmed_at IS NOT NULL`. NULL means "settled for exactly `amount`" — which is **every legacy row, every exact receipt, every captured payment and every cash-on-delivery confirmation**, so there is **no backfill**. Domain: `Payment::settledAmount(): Money` (`settled_amount ?? amount`) and `confirm(DateTimeImmutable $at, ?Money $acceptedAmount = null, ?string $reason = null)` (both optional arguments together, positive, same currency; every existing call unchanged). `payments.amount` stays the **expected** amount and never changes.
- **`order_events`** gains two nullable FKs, `payment_id` and `payment_receipt_id` (names `oe_payment_fk`, `oe_payment_receipt_fk`; the same pattern as `payment_refund_id`), so the three new event types point at their records. The existing `operation_key` + payload hash carry idempotency.
- **More than one receipt per payment — SUPPORTED now (decided).** A transfer paid in two parts is ordinary for bank customers and the table makes it free; the first part is simply "short by X" in the list, and the second settles it by itself when the sum matches. *Cost:* the effective-sum read and the 20-row limit. *Refusing it now* would force the merchant to "accept" a shortfall that is only a part, then handle the rest as an overpayment — wrong facts, worse trail.

**3. The receipt operation** — `PaymentReceiptRecorder::record(paymentId, Money $amount, string $receivedOn, string $reference, DateTimeImmutable $occurredAt, ?string $operationKey)`.

- **Only bank transfer** (`method = bank_transfer`; others are refused by name — cash on delivery is R10/R4b). The payment must be `isConfirmable()` (pending, answered, unconfirmed, unvoided); a settled, voided or unanswered one is refused by name.
- **Order of work, in one transaction:** read the payment (to find the order), **lock the order** (`findByIdForUpdate`), **replay by operation key** (same key and hash → the first result, nothing written, no hook; other contents → `OperationKeyReusedException`), then validate, then write. The unique `(order_id, operation_key)` index is the backstop, with the same one-retry as the refunds.
- **Validation (all translated refusals, nothing written):** amount > 0, parsed by `MoneyInput` (≤ 32 characters, ≤ 9 integer digits) in the payment's currency; **received day** = a real `Y-m-d`, **not after today and not before the order's placement day, both in the store timezone** (`StoreTimezone`, compared as text, under the lock; never shifted); reference non-blank, ≤ 64; effective receipts after this one ≤ 20.
- **Exact match** (`sum + amount = expected`): the receipt row, then `OrderPaymentConfirmer::confirmWithinOpenTransaction()` (one implementation of settling — `confirmed_at` = the instant of recording, as today) → events `payment_receipt_recorded` (carries the key) + the existing `payment_confirmed`; hooks `order.payment_receipt_recorded` and `order.payment_confirmed`. The payment is settled exactly as it is today, plus the recorded facts; `settled_amount` stays NULL.
- **Mismatch — short or over** (`sum + amount ≠ expected`): the receipt row and the event `payment_receipt_recorded` only; **the payment is NOT settled** (R9 still blocks shipping), `confirmed_at` stays NULL, the order appears under "needs attention" (§4). Short and over are the same state with a signed difference.
- **While a receipt is unreconciled, the money is in hand:** `cancel()`, `recordReturn()` and `OrderEditor::apply()` are **refused by name** (`PaymentReceiptUnreconciledException`, translated: "A transfer of X was received for this order and has not been reconciled — accept it or record the rest first"). Without this a cancel would *void* the payment and orphan the money. The way to cancel is to accept the mismatch (the payment becomes settled for the received amount), after which the ordinary refund path returns it.

**4. Resolving a mismatch.**

- **(a) Accept** — `PaymentReceiptRecorder::acceptMismatch(paymentId, string $reason, …, ?string $operationKey)`: **mandatory reason ≤ 255** (the `settlement_reason` column); only for an unsettled, unvoided bank payment with ≥ 1 effective receipt and `sum ≠ expected`; the payment is confirmed with `settledAmount = sum` and the reason; events `payment_mismatch_accepted` (reason, payment id) + `payment_confirmed`; hooks `order.payment_mismatch_accepted`, `order.payment_confirmed`. Permission: §5.
- **(b) Leave unsettled** — no operation; the item stays listed with its growing age; shipping stays blocked; cancel/return/edit stay refused (§3).
- **What "settled for exactly that amount" does.** `payments.amount` and `orders.total` **do not change** (the concession is a fact on the payment, not a price change). **Every cap that used the payment's amount uses `settledAmount()`**: the total cap (`RefundCapGuard::totalRoom`), "paid in" (`OrderRefundsReader`) and the "Paid" row of the money summary — three one-line changes, all behind the same accessor. **Standing rule, for every future report or screen that shows what was paid in: read `Payment::settledAmount()`, never `amount()`** — `amount()` is the *expected* amount (the order's price) and stays so. Per-line and shipping caps are untouched. *Underpaid and accepted (90 of 100):* the total cap is 90, so a refund of the goods' computed share can exceed it and is refused; the merchant enters a smaller goods amount (the dialog's goods boxes are editable) — which is the point. *Overpaid and accepted (110 of 100):* the total cap is 110; the 10 surplus is refundable only through a **money-only refund** (`adjustment`), since the line and shipping caps are unchanged. A refund cannot exist before acceptance (refunds need a settled payment), so nothing already refunded can be contradicted by the acceptance.
- **Corrections — DECIDED: two kinds, one operation** (`PaymentReceiptRecorder::correct(receiptId, Money, receivedOn, reference, reason, …)`). A correction appends a new receipt that `supersedes` the old one (the existing `UNIQUE prc_supersedes_unique`: an effective receipt is superseded at most once, and a chain of corrections is a chain of such rows); nothing is edited or deleted. It runs like every write here: the order lock first, the replay by operation key, one history event, the hook after the commit, translated refusals. The reason is **mandatory, ≤ 255**, and a correction that changes nothing at all (same amount, day and reference) is refused by name (`nothing_to_correct`). Only an *effective* receipt can be corrected, on a bank-transfer payment that is not voided. The total-rows limit of §2 applies (`too_many_receipt_rows`).
  - **(i) Before settlement** (unchanged): amount, day and reference may all change, and the result is re-evaluated like a new receipt — a correction that makes the effective sum equal the expected amount settles the payment (the same exact-match path: `payment_confirmed` event and hook).
  - **(ii) After settlement — DECIDED by the owner (2026-10-05): the DAY and the BANK REFERENCE may be corrected, provided the AMOUNT is unchanged.** *Why:* the reference is what the merchant reconciles against the bank statement, so a typo in it must not be permanent; and changing the day or the reference touches **nothing the write-once commitments protect** — `confirmed_at` records the *settlement* (a payment fact), not the receipt's facts; the effective sum, `settled_amount_minor`, `settlement_reason` and every cap are the same before and after. *What it does:* the new amount must equal the superseded receipt's amount, otherwise the correction is **refused by name, translated** (`receipt_amount_change_after_settlement`: "An amount cannot be corrected after settlement"); the new day is validated exactly like a new receipt's (a real `Y-m-d`, not after today, not before the order's placement day, both in the store timezone); the reference is non-blank and ≤ 64; the new row supersedes the old one; **the payment stays settled and is not touched** — `confirmed_at`, `settled_amount_minor` and `settlement_reason` keep their values; **there is no re-evaluation of settlement, no `payment_confirmed` event and no `order.payment_confirmed` hook**; the only trail is the event `payment_receipt_corrected` (reason, staff member, `payment_id`, the new `payment_receipt_id`) and the hook `order.payment_receipt_corrected`. Permission: `ORDER_MANAGE`, the same as recording (§5). It applies equally to an exact settlement and to an accepted mismatch.
  - **A wrongly entered AMOUNT on a settled payment is still not correctable** (`confirmed_at` is write-once and the cap base is built on it): it is put right through the money trail — a refund or a money-only refund — not by editing history. The rule that must hold whenever a correction changes an amount — **a correction can never leave `received < already refunded`** — is therefore satisfied by construction: amounts change only before settlement, where no refund can exist, and never after it.
  - **Legacy confirmed payments have no receipts**: there is nothing to correct on them, and R4a does not invent a receipt to be corrected.

**5. Permissions, audit, hooks.**

- **Record a receipt (and correct one): `ORDER_MANAGE`**, unchanged from today's "mark as received" (recording that money arrived pays nothing out; Manager keeps it). **Accept a mismatch: a money decision** — it gives money away (an underpayment forgiven) or takes it on (an overpayment to be refunded) — **decided: a new permission `payment_reconcile`, Administrator-only**, with the recipe above (enum, seeder, migration into the existing Administrator row, role label en+bg, migration test). *Cheaper alternative:* reuse `REFUND_BANK` (Administrator-only today), zero infrastructure, but a permission named "refund by bank" would gate "accept a short transfer" and read wrongly on the roles page.
- **History** (three new `order_events` types, labels en + bg; each with the staff member, `payment_id`, `payment_receipt_id` where it applies): `payment_receipt_recorded` (reason = the bank reference), `payment_receipt_corrected` (reason = the correction's reason; written for both kinds of correction, and **alone** after settlement — never with a `payment_confirmed`), `payment_mismatch_accepted` (reason = the acceptance reason). The existing `payment_confirmed` accompanies a settling operation.
- **Hooks** (Actions, app layer only, after commit, never on a replay or a refusal; rows go into `extensibility-coverage-design.md` and the Hook Reference *when built*): `order.payment_receipt_recorded (Order, Payment, PaymentReceipt)`; `order.payment_receipt_corrected (Order, Payment, PaymentReceipt $new, PaymentReceipt $superseded)` (the **only** hook a correction after settlement fires); `order.payment_mismatch_accepted (Order, Payment, string $reason)`. `order.payment_confirmed (Payment)` is unchanged and fires once per settlement, including an accepted one.

**6. "Needs attention" — derived from facts, never a stored flag.**

- **Why derived:** a flag is a second copy of a fact that can drift (a refund paid out, a receipt completed) and needs a writer on every path; the facts — OWED refunds, receipts on an unsettled payment — are already the truth, and §7.2.7 forbids thresholds, so there is nothing to store.
- **R4a ships two sources.** *OWED refunds*: `payment_refunds.status = 'owed'`, **days since created** (calendar days in the store timezone, `StoreTimezone::daysBetween`), **oldest first**. *Receipt mismatches*: unsettled, unvoided bank payments whose effective receipts sum to something other than the expected amount, with expected / received / signed difference and **days since the earliest effective receipt's `received_on`**, oldest first. **Age is a plain number; no severity, no colour, no threshold, no "overdue".** An index `payment_refunds (status, created_at)` is added for the first source (none exists).
- **The extension point R4b uses**: `interface NeedsAttentionSource { key(); label(); count(): int; page(int $page, int $perPage): list<NeedsAttentionItem> }`, bound in the container with a tag; `NeedsAttentionItem` is a value object (source key, order id, a one-line fact, amount and currency, age in days, the day it started). R4b adds its two COD sources (collected-not-remitted by days since collected; remittance mismatches) by tagging two more classes; a **filter hook** `admin.needs_attention.sources` for merchant extensions is reserved, not built.
- **Where it lives:** one admin `Page` ("Needs attention", `NavigationGroup::SALES`, after Orders, `ORDER_VIEW`, `canAccess()` re-checked at mount), one section per source, **25 rows per page and an independent paginator per source**, newest-last never — oldest first; each row links to the order. Query budget: per source one `COUNT` and one page query (≈ 4 reads + auth). **No navigation badge in R4a**: a badge would run its counts on *every* panel page and move the query pins of unrelated pages (the Sandbox list at 19, the product lists, every order pin); decided instead: the count on the page itself, and a banner in the order's payment/refund sections (which read facts the page already loads). **Deferred — not R4a:** the page is only seen when someone opens it, so a count the merchant sees without opening it is recorded as a later addition, in one of two forms over the same sources: **a navigation count with a short cache (minutes)**, so the counts are not run on every panel render, or **a small dashboard block** (the stock dashboard has room for one). It is out of R4a because an uncached count would change the query pins of every unrelated panel page (the Sandbox list at 19, the product lists, every order pin), and a cached one needs its own invalidation rule and tests. No order-list filter, and **no dashboard widget in R4a**: the dashboard exists but is the stock one, a widget would add its own queries to the landing page, and the Needs-attention page is the one place the facts are listed (a widget over the same sources is a later, cheap addition).
- **Order page:** the payment block shows expected, received so far, the receipts (day, amount, reference, who) and, for a mismatch, one neutral line "short by X / over by X"; a settled bank payment without receipts shows "received amount not recorded (before receipts were kept)". The receipts are read **only for a bank-transfer latest payment** (one grouped query), so cash-on-delivery pages keep their pins. Pins expected to move for bank-transfer fixtures, **to be measured and reported, never edited silently**: `OrderAdminReaderTest` / `OrderAdminReaderEventsTest` (the 12-query forOrder pin), `OrderViewPageTest`, `OrderViewActionsTest`, `OrderRefundsSectionTest`, `OrderResourceTest`, `OrderCancelReturnActionsTest` (page load 18, dialog mounts).

cancel, return and edit are refused while a receipt is unreconciled and work after acceptance; a correction supersedes and can settle; a correction that changes the amount is refused after settlement, and a correction of the day or the reference with the same amount is accepted after settlement and leaves `confirmed_at`, `settled_amount_minor`, the effective sum and every cap unchanged (the old row stays as the superseded one, the event names the reason and the staff member), including on an accepted mismatch; a correction without a reason, with a malformed day, a day before the placement day or after today, or a 65-character reference is a field error; **a correction of the day and of the reference after an exact settlement is accepted and changes nothing money-wise (`confirmed_at`, `settled_amount_minor`, `settlement_reason`, the effective sum, `totalRoom()` and every cap are identical before and after, no `payment_confirmed` event and no `order.payment_confirmed` hook fire, exactly one `payment_receipt_corrected`); the same after an accepted mismatch; a changed amount after settlement is refused by name; a correction that changes nothing is refused; the 51st row of a payment (superseded ones counted) is refused by name while the 21st effective receipt is refused independently, and a correction never raises the effective count; a superseded receipt is ignored by the effective sum, by the settlement check and by the needs-attention age (the age is counted from the earliest EFFECTIVE receipt's day, so correcting a day moves it); a legacy settled payment has no receipt to correct;** the effective sum ignores superseded rows. *Legacy:* a confirmed payment with no receipts is settled for its amount and never listed. *Needs attention:* OWED refunds appear oldest first with calendar-day ages (Europe/Sofia midnight cases); a mismatch appears with its signed difference and age; a paid-out or cancelled refund and a settled payment disappear; no row carries a severity; the page paginates per source; the count queries are bounded. *Pins:* bank-transfer order pages gain exactly the one receipts read; cash-on-delivery pages gain none.

**11. Decisions (owner, 2026-10-05).** All 13 recommendations were **ACCEPTED**, with **one change, to (4)**: a correction of the day or the bank reference is allowed after settlement too, with the amount unchanged (§4). They are decided and no longer open: (1) several receipts per payment — **supported**; (2) the bank reference — **required**; (3) accepting a mismatch — **a new `payment_reconcile` permission, Administrator-only** (alternative: `REFUND_BANK`); (4) corrections — **any field while unsettled; after settlement only the day and the reference, with the amount unchanged** (a change of amount after settlement stays refused; the owner's change to the recommendation, which refused every correction after settlement); (5) cancel/return/edit while a receipt is unreconciled — **refused until accepted**; (6) cash on delivery keeps today's one-click confirm until R4b; (7) **no navigation badge** and no dashboard widget in R4a (the stock dashboard stays as it is); (8) legacy confirmed payments — **expected = received, nothing recorded, never flagged**; (9) `confirmed_at` stays "when the merchant recorded it" and the *day the money arrived* is `received_on`; (10) an accepted overpayment returns its surplus through a money-only refund; (11) no tolerance — an amount differs or it does not; (12) at most 20 effective receipts per payment; (13) the order total is **not** changed by an accepted underpayment.


#### 7.2.21 What R4a-2 built (the bank-transfer receipt service)

*Built 2026-10-05 on top of R4a-1 (§7.2.20 §9). Still no dialog, no `acceptMismatch()`, no `correct()`, no permission change.*

- **`PaymentReceiptRecorder::record(paymentId, Money, receivedOn, reference, occurredAt, ?operationKey)`** (`app/Services/PaymentReceiptRecorder.php`) exactly as §3: one transaction, the payment's order **locked first**, the replay by operation key (same key and contents: the first result, nothing written, no hook; other contents: `OperationKeyReusedException`; the unique `(order_id, operation_key)` is the backstop with the same one retry as the refunds), then the checks, then the writes. The payment is read once **outside** the transaction (only to find the order to lock) and again under the lock: a plain read inside the transaction before the lock would open MySQL's consistent snapshot early and hide a receipt committed by the call that held the lock. The key and the payload hash (`RefundOperationFingerprint::forReceipt`: payment, amount, currency, day, cleaned reference) sit on the `payment_receipt_recorded` event, which carries `payment_id` and `payment_receipt_id`.
- **Refusals by name, translated en + bg** (`PaymentReceiptRefusedException`, `orders.payment_receipt.refused.*`; every one carries the form field it belongs to: `amount`, `received_on`, `bank_reference`, or none): not a bank transfer, settled, voided, unanswered (or otherwise not confirmable); amount not positive, more than 9 integer digits (`MoneyInput`'s limit; the service takes `Money`, the text goes through `MoneyInput` first), another currency than the payment's; day not a real `Y-m-d`, after today, before the order's placement day (both **store-timezone** days, compared as text, inclusive, never shifted; "today" is the day of `occurredAt`, as in `recordReturn()`); reference blank (also only non-ASCII whitespace, e.g. U+00A0, U+200B, U+FEFF), longer than 64 characters, invalid UTF-8, or holding control/invisible-format characters; a 21st **effective** receipt, a 51st **row** (superseded counted) — independent limits, both under the lock.
- **Exact match** (effective sum + amount = expected): the receipt row, the `payment_receipt_recorded` event, then `OrderPaymentConfirmer::confirmReconciledWithinOpenTransaction()` — the same settling code as ever (`confirmed_at` = the instant of recording, `settled_amount` stays NULL) — which writes the existing `payment_confirmed` event. Hooks after commit: `order.payment_receipt_recorded (Order, Payment, PaymentReceipt)`, then `order.payment_confirmed (Payment)`.
- **Mismatch** (short or over): the receipt row and the `payment_receipt_recorded` event only; the payment is **not** settled; only `order.payment_receipt_recorded` fires.
- **`PaymentReceiptReader` / `PaymentReceiptStatus`** (`app/Services`): the one source for expected, effective sum, signed difference (received − expected), number of effective receipts and the state (`none | partial | mismatch | settled`; partial = 0 < sum < expected, mismatch = sum > expected). `withReceipt(Money)` answers "what would it be with one more receipt", which is both the service's exact-match test and the future dialog hint, so no arithmetic exists anywhere else. `unreconciledSum()` / `assertReconciled()` are the guard's questions: a bank-transfer payment that is not settled, not voided, with an effective receipt — at most one grouped read, none for any other payment.
- **`PaymentReceiptUnreconciledException`** (translated, names the amount received): thrown by `OrderStatusChanger::cancel()` and `recordReturn()` (after the replay and the status check, before any write), by `OrderEditor::apply()` (after the status and settled-payment gates), and by the old one-click confirmation. The panel's cancel / return / mark-as-received handler and the edit handler show it as a refusal notice, never a 500.
- **The gap the document did not name, closed here:** the one-click "mark as received" for a bank transfer goes through `OrderPaymentConfirmer`, which would settle for the full expected amount over a receipt that does not match it. `confirm()` and `confirmWithinOpenTransaction()` now refuse a bank-transfer payment with an effective receipt; the receipt service settles through a **second public method with its own name**, `confirmReconciledWithinOpenTransaction()`, sharing one private implementation with the first (a separate method, not a boolean a caller could pass by mistake). Cash on delivery and R10 never reach the check (no receipt read). **R4a-4 replaces the one-click with the dialog; this refusal then becomes a backstop.**
- **History and hooks.** `order_events.type` is a plain string column (no enum, no CHECK), so **no migration was needed**; `OrderEventType` gained `payment_receipt_recorded` and, for R4a-3, `payment_receipt_corrected` and `payment_mismatch_accepted` (labels en + bg for all three; nothing writes the last two yet). `OrderEventRecorder::record()` gained `paymentId` and `paymentReceiptId`. The hook row of `order.payment_receipt_recorded` is in `extensibility-coverage-design.md` and `extensibility-design-and-hooks.md`.
- **Not built (by design):** `acceptMismatch()`, `correct()`, the `payment_reconcile` permission, every dialog, the order-page entries, the needs-attention page.
- **Queries.** Cancel and return read the order's payments once before the refund path (`findByOrderId`), plus one grouped receipt sum for a pending bank-transfer payment: the cancel bound in `OrderStatusChangerTest` moved from 20 to 21 (reported, not edited). The edit reads nothing extra (it already has the payments).


#### 7.2.22 What R4a-3 built (resolving a mismatch)

*Built 2026-10-06 on top of R4a-1 and R4a-2 (§7.2.21). Still no dialog and no admin action (R4a-4), no needs-attention page (R4a-5); `record()`, the one-click "mark as received", cash on delivery, R10 and the cap-base readers are unchanged.*

- **Permission `payment_reconcile`, Administrator only.** Enum case, `StaffSystemRolesSeeder` (Administrator only), the role-page group "Orders" and its label (en + bg, `lang/*/roles.php`), and the data migration `2026_10_09_000001_add_payment_reconcile_to_administrator_role` (Staff package; the product-delete recipe: it writes the `staff_roles.permissions` json of the shipped Administrator row only — `name = 'Administrator' AND is_system`, never Manager, idempotent, `down()` removes exactly this value). Tested in `AddPaymentReconcileToAdministratorRoleMigrationTest`.
- **`PaymentReceiptRecorder::acceptMismatch(paymentId, Money $acceptedAmount, string $reason, occurredAt, ?operationKey)`** (§4a). **The service enforces the permission itself** through `PaymentReconcilePolicy` (the twin of `RefundPermissionPolicy`: `PanelStaffActor` + `AuthenticatedStaffResolver`, fail closed — no acting staff member is a refusal), thrown as the translated `PaymentReconcilePermissionDeniedException` before the lock, so a caller that bypasses the panel is stopped. Then the same shape as `record()`: payment read outside the transaction only to find the order, order lock first, replay by key (fingerprint: action, payment, the accepted figure, the reason), payment re-read under the lock, checks, writes. Refused by name (`PaymentReceiptRefusedException`, translated, with the form field): not a bank transfer, settled, voided, unanswered; `no_effective_receipt`; `nothing_to_accept` (the sum equals the expected amount); `accepted_amount_changed` (field `accepted_amount`; the message names the current sum — a receipt arrived or was corrected between the dialog and the submit; another currency counts as changed); reason blank / over 255 / holding control or invisible-format characters (`reason_blank`, `reason_too_long`, `reason_invalid`, field `reason`; the same cleaning as the bank reference, via one shared private routine). On success: the event `payment_mismatch_accepted` (reason, payment id, key, hash; no receipt id) and the payment confirmed with `settledAmount` = the sum and the reason through a **new named method** `OrderPaymentConfirmer::confirmAcceptedWithinOpenTransaction()` (same private implementation as the other two; the one-click path stays refused), plus the usual `payment_confirmed`. Hooks after commit: `order.payment_mismatch_accepted (Order, Payment, string $reason)`, `order.payment_confirmed (Payment)`. `payments.amount` and `orders.total` do not change; the caps read `settledAmount()` (R4a-1), so after accepting 90 of 100 the total room is 90 and after 110 of 100 it is 110.
- **`PaymentReceiptRecorder::correct(receiptId, Money, receivedOn, reference, reason, occurredAt, ?operationKey)`** (§4 "Corrections", both kinds, one operation). Receipt → payment → order found outside the transaction; order lock; replay (fingerprint: receipt, amount, day, reference, reason); everything re-read under the lock. Refused by name: `receipt_unknown`, `receipt_not_effective` (already superseded), not a bank transfer, voided, `nothing_to_correct` (amount, day and reference all unchanged), `too_many_receipt_rows` (the 50 limit; the 20-effective limit is not re-checked), and every amount / day / reference / reason refusal of `record()` (same private validators). The new row supersedes the old one. **(i) Before settlement** any field may change and the result is re-evaluated through `PaymentReceiptStatus::withReceiptReplaced()` (the one place of that arithmetic): equal to the expected amount settles through `confirmReconciledWithinOpenTransaction()` (events `payment_receipt_corrected` + `payment_confirmed`, hooks `order.payment_receipt_corrected` + `order.payment_confirmed`), otherwise only the correction event and hook. **(ii) After settlement** (exact or accepted) only the day and the reference: a different amount is `receipt_amount_change_after_settlement` (field `amount`); the payment row is not written at all, there is no `payment_confirmed` event and no `order.payment_confirmed` hook — only `payment_receipt_corrected` (reason, staff, `payment_id`, the NEW `payment_receipt_id`) and `order.payment_receipt_corrected (Order, Payment, PaymentReceipt $new, PaymentReceipt $superseded)`. `correct()` has no permission check of its own: `ORDER_MANAGE` stays the action's, exactly as for `record()`.
- **Shared, not copied:** the lock + replay skeleton of the two new operations is one private method (`underOrderLock`), the one-retry on a duplicate key another (`withDuplicateRetry`); `record()` keeps its own code path unchanged.
- **History and hooks:** the event types `payment_receipt_corrected` and `payment_mismatch_accepted` and their labels (en + bg) were declared in R4a-2 and are written now; the two hook rows are in `extensibility-coverage-design.md` and `extensibility-design-and-hooks.md`. No migration for events (the type column is a plain string).
- **What "released" means for cancel / return / edit after an acceptance:** the unreconciled refusal is gone; the ordinary rules speak. A cancel or return is capped at what was settled (an accepted 90 of 100: the goods share of 100.00 is refused by the total cap and the merchant enters a smaller goods amount; an accepted 110: the goods go back and the 10.00 surplus stays refundable through a money-only refund). An edit is refused by the settled-payment gate (E3), as for every settled order.
- **Not built:** every dialog and admin action, the order-page entries, the needs-attention page.

## 8. Promotions do not touch shipping. At all.

Domain-owner decision, in his own words: a promotion code is a discount **on products only**.

So: no promotion type discounts shipping, no "free shipping" promotion exists, and `discountMinor` never includes a shipping component. `promotions-domain-design.md` needs no change — this section exists so that nobody later adds a `FREE_SHIPPING` discount type believing it was merely an oversight.

The interaction that *does* exist is §5.1's: a promotion changes the basis the free-shipping threshold is measured against. That is a threshold rule, not a discount on shipping, and the distinction matters — the customer's shipping line either is free or costs its full price; it is never partially discounted.

## 9. Where this sits in checkout

Rate resolution happens while the customer is choosing, before anything is written:

1. The delivery address is known (typed or chosen) → match a `ShippingZone` (§4).
2. List that zone's active methods → compute each one's amount (§5), FLAT and FREE and PER_CLASS locally, CARRIER through a provider (§6).
3. The customer picks one. A method with `requiresPickupPoint` also demands an office, which `Address` already stores.
4. At placement, `CheckoutOrchestrator` snapshots the chosen method's name, code and amount onto the `Order` (§7), inside Phase 1's transaction, with the amount **recomputed server-side** and never taken from the client — the same rule the line prices already follow, for the same reason: the customer must pay what he was shown, and the server must be the one that decides what that is.

If the recomputed amount differs from what the customer was shown, placement **refuses** with a clear message rather than charging the new figure — exactly the posture already taken for a promotion code that went invalid between the cart and the checkout. The customer must never press "Pay" seeing one total and be charged another.

## 10. Explicitly out of scope for V1 (deferred, not forgotten)

- **Every carrier integration** — Econt, Speedy, BoxNow. The whole point of §6 is that these are additions.
- **Weight-based rates** — domain-owner decision, "later". `weightGrams` already exists; a `WEIGHT` kind is one enum case and one rate table when it is wanted.
- **Volumetric / dimensional pricing** — same, and it needs the dimensions the UI does not yet collect.
- **The product/variation shipping-fields UI** — `product-shipping-fields-note.md` already maps where they go in both forms; that note stays the guide.
- **Multi-parcel splitting** — one order, one shipping charge (§3.1).
- **Re-quoting shipping when an order is edited** (§7).
- **Shipping tax** — no tax domain exists; `Price` carries a tax rate but nothing applies it to shipping.
- **Local pickup from the shop itself** — expressible today as a `FREE` method, so no separate kind is built for it.
- **Per-location / multi-warehouse origin** — Shopify's delivery profiles exist for this; a single-shop V1 has no use for it, and nothing here precludes it.

## 11. Testing plan

- `ShippingClass` / `ShippingZone` / `ShippingMethod` domain unit tests: construction and validation; a `PER_CLASS` method with no rate for a class falls back to `amountMinor`; a `FLAT` method rejects a negative amount; a method with `freeAboveMinor` set and `kind: FREE` is rejected as contradictory.
- **Zone matching, as a real matrix**: an address matching two zones takes the one with the lower `sortOrder`; an address matching none is refused, with the refusal asserted rather than an empty list; a `PICKUP_POINT` address matches on `settlement`.
- **§3.1's most-expensive rule, which is the single most important test in this document**: a cart with three classes charging 3, 7 and 5 is charged **7**, asserted explicitly as *not* 15. Name the test after the rule so a future "fix" to summing fails loudly.
- **§5.1's threshold basis**: a cart whose pre-discount subtotal clears the threshold but whose post-discount total does not is charged for shipping — asserted as the specific number, not merely "shipping is non-zero". And the reverse case. This is the rule most likely to be implemented against the wrong figure.
- **§7's formula**: `Order::create()` computes `subtotal - discount + shipping` and still refuses a supplied total; an order with zero shipping produces exactly the old number, so existing expectations hold.
- **§9's recompute-and-refuse**: a method whose amount changes between quoting and placement refuses the order and writes nothing — the same shape as the existing promotion-no-longer-valid test, which it should mirror.
- **§8**: a promotion never reduces `shippingMinor`, asserted directly.
- Real MySQL Feature tests for each repository; a `SHOW CREATE TABLE` confirmation of the new `orders.shipping_minor` column and of the zone/method foreign keys.
- `ShippingRateProvider` is **not** tested against a real carrier — there is none. A fake provider in the test suite proves the resolver refuses an unknown carrier code and never falls back to a default, mirroring `PaymentMethodAdapterResolver`'s own tests.
