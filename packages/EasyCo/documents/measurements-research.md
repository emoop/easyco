# MEAS-0 — measurement templates («Индивидуални размери») and variation weight: research

Status: RESEARCH ONLY (2026-11-13). No code was written, no migration, no commit. Facts carry `file:line` (verified in the tree at commit `06c9c68`); everything marked **PROPOSAL** is a recommendation, not a decision.

## 0. What was decided by the owner (recorded, not re-opened)

1. **Measures (показатели):** a merchant list, name + unit chosen once.
2. **Templates (шаблони):** a named, ordered list of measures.
3. **Product:** pick ONE template; a grid of rows = the product's variations (size value comes from the variation itself, no second list of sizes), columns = the template's measures; the merchant types numbers only. A simple product has one row.
4. **Storefront:** a product section (accordion / tab) prints it as a TABLE (TBL-1 look: `sf-table-wrap`, sticky first column, scroll shadow). Empty cells / empty rows are not shown; a product with no values shows nothing.
5. **Weight:** optional, per variation, NEVER shown; for the later courier integration.
6. Agreed in principle (feasibility answered in §E.5): switching a template keeps the numbers (hidden), adding a measure to a used template adds an empty column, «Копирай от друг продукт».

## 1. The five most important findings

1. **Weight is already half-built.** `catalog_variations.weight_grams` (nullable unsigned int) plus `length_mm / width_mm / height_mm` exist since the first Catalog migration (`packages/EasyCo/Catalog/database/migrations/2026_08_23_000006_create_catalog_variations_table.php:60`), `Variation::weightGrams()` and `setDimensions()` exist (`packages/EasyCo/Catalog/src/Variation.php:402-418`), the repository persists them (`EloquentProductRepository.php:402-403`, `EloquentVariationRepository.php:190`), and `ShippingQuoteService` already SUMS them into the carrier quote context (`app/Services/ShippingQuoteService.php:256-266`: unknown weight on any line ⇒ the whole weight is `null`, never 0). **No admin screen writes it** (nothing in `app/Filament` calls `setDimensions`/mentions weight for a variation), and **nothing snapshots it at sale**. So «weight first» needs NO migration for the variation; it needs an admin field and an order snapshot.
2. **The frozen files do not block anything.** All the data can hang off `catalog_variations.id` / `catalog_products.id` / `catalog_attribute_values.id` in own tables; the weight needs only existing setters. The one product-level fact the page must know for free (the chosen template) can be a plain column on `catalog_products` written by an app service, exactly like the derived `price_from_minor` / `is_available` columns (`app/Services/PriceSort/ProductSortPriceRefresher.php`), so `Product.php` is not touched.
3. **«The size» of a variation is not a thing in the model.** A variation has 1..n attribute assignments (`Variation::attributeAssignments()`, `Variation.php:181`; table `catalog_variation_attribute_values`, one value per axis, unique per variation+axis `…2026_08_23_000011…`), the storefront label is just the values joined with « / » (`CatalogReader.php:163`) and the admin label is «Axis: value, …» (`EditVariableProduct.php:2130`). Nothing says which axis is the size. A product with size + colour has one variation per combination, so «rows = variations» would repeat the same numbers per colour. **PROPOSAL (§A):** key the numbers by the *size value* (the attribute value of one chosen axis), not by the variation; mark the size attribute once on the attribute definition.
4. **`catalog_size_guides` / `catalog_products.size_guide_id` is a dead stub** (`…2026_08_23_000002…`, `…000005…:25`; `catalog-domain-design.md:27,1454` «extension point … no measurement rows table yet»; `EditVariableProduct.php:144-145` «size_guide_id (still not wired…)»; no PHP uses it except the model's `$fillable`, `ProductModel.php:33`). It is the natural slot this feature was reserved for, but it is a *scope* concept (universal / brand / category / product), not a template. **PROPOSAL:** leave it; new tables; decide in MEAS-1 whether to drop the stub in a separate, explicit task (not now).
5. **A P4b section source is a small, well-fenced extension** (`SectionSet::SOURCES`, `SectionSet.php:34`; the resolver's `match`, `SectionResolver.php:41-49`; the compiler keeps a per-source shape, `SectionCompiler.php:139-175`) and the `blocks` / `meta` sources are exact precedents for «built from product data, not from a stored text». The product page can know *for free* whether a product has a template if the template id is a column of the product row the page already loads (`CatalogReader::product()` select, `CatalogReader.php` ~l.95): products with no template then cost **0** statements and the pinned counts cannot move.

## A. Variations and the size value

**Storage today (Step 0 facts).**
- `catalog_variations` (`…000006…`): `product_id` (RESTRICT), `type` (`universal` | `standard`), `status`, `attribute_signature` (sha256, unique per product `catalog_variations_product_signature_unique`), `sku` (unique), `barcode`, `is_visible`, `is_purchasable`, `shipping_class`, `weight_grams`, `length_mm`, `width_mm`, `height_mm`, soft deletes, and `sort_order` (merchant's order, `2026_09_23_000001…`).
- Axes: `catalog_product_attributes` (descriptive attributes AND axis declarations, `is_variation_axis`), `catalog_product_axis_values` (allowed values per axis), `catalog_variation_attribute_values` (the chosen value per axis, FK to definition + value, both RESTRICT). Values: `catalog_attribute_values` (`value` string, `sort_order`, `colour`, picture; unique per definition). Definitions: `catalog_attribute_definitions` (`code`, `name`, `type`, `is_filterable`, `filter_display`, `display_type` = dropdown | buttons | swatch | specs). Domain: `AttributeDefinition` (`packages/EasyCo/Catalog/src/AttributeDefinition.php:28-36`, NOT frozen).
- A SIMPLE product has exactly one `universal` variation (never customer-selectable); a VARIABLE product has `standard` variations only. What the storefront shows: `StorefrontVisibility::variations()` (`app/Storefront/Visibility/StorefrontVisibility.php:109-123`: not deleted, status active, and for variable products `is_visible`).
- Admin: the variable product's «Вариации» tab is a `Repeater` `existing_variations` (`EditVariableProduct.php:1291`), its rows built by `existingVariationRows()` (`:2054`) and written by `updateVariationRows()` (`:3044`) through the domain setters + `ActivityLogger::logFieldChanged` + `Hook::apply('catalog.variation.barcode')`.

**How rows should be formed (PROPOSAL).**
- **One row per distinct SIZE VALUE, not per variation.** The size value is `catalog_attribute_values.id` of ONE axis of the product. A product with only a size axis: one row per size, in the value's `sort_order` (so «S, M, L» and «5-6 г. (110 см)» come out in the merchant's own order — no second list). A product with size + colour: still one row per size (the colour does not change a garment's measurements); two sizes × three colours = two rows, not six. A product whose only axis is colour (or any single non-size axis): one row per value of that axis (works, harmless). A SIMPLE product: one row, labelled with the template's own «Размери» heading (no size label).
- **Which axis is «the size»:** add one nullable flag to `catalog_attribute_definitions`, e.g. `is_size` (boolean, default false), set once in the attribute screen (`AttributeDefinitionResource`) and carried by `AttributeDefinition` (the same pattern as `is_filterable` / `display_type`, migrations `2026_10_27_000003/4`). Row axis of a product = the declared axis flagged as size; if none is flagged, the FIRST declared axis; if the product has several flagged axes, the first by definition id. The grid shows the axis it used in its title so the merchant sees the rule at work. (Alternative considered: a per-product choice. Rejected for V1: one more thing to click per product; a flag is set once per shop.)
- **Why not variation-keyed rows:** variations are archived / restored / regenerated by the axes workflow (`EditVariableProduct.php` axes tab, `restructureAxes` `:906`), and `DuplicateProduct` NEVER copies variations of a variable product (`app/Services/DuplicateProduct.php` docblock, «variations are NEVER copied, full stop»). Numbers keyed by variation id would be lost on every restructure and could never be copied to a duplicate; numbers keyed by (product, size value id) survive both, and «Копирай от друг продукт» maps by value id / value text.

**Attaching data without the frozen files.** Own tables keyed by `product_id` and `attribute_value_id` (see §E); a column on `catalog_products` for the chosen template (app-service write, like `price_from_minor`); weight on the existing `catalog_variations.weight_grams` through `Variation::setDimensions()` (not frozen-file edit: the method exists). `Product.php`, `Variation.php`, `VariationSignature.php` stay untouched.

## B. Weight today

- **Exists:** variation `weight_grams` + three dimensions in mm (see finding 1); the shipping package already treats weight as «nullable, null = unknown, never zero» (`shipping-domain-design.md:244`; `packages/EasyCo/Shipping/src/Carrier/ShippingContext.php:24,39,51`) and a carrier waybill request has `weightGrams` (`Carrier/ShipmentRequest.php:47,69`). `ShipmentLabelProvider` («creates a shipment … Nothing in V1 calls it») is the future one-click-waybill contract. Weight-based RATES are a decided «later» (`shipping-domain-design.md:143,1123`; a `WEIGHT` method kind is «one enum case and one rate table»).
- **Does NOT exist:** a product-level default weight; any admin UI for weight or dimensions; any snapshot on the sold line. The sale line snapshots price, discounts, cost and `sold_attributes` (`2026_09_24_000001_add_snapshot_fields_to_operational_sales_sale_lines_table.php`; built by `app/Services/SaleLineSnapshotBuilder.php`) and the order has shipping facts (`2026_10_09_000003_add_shipping_facts_to_orders_and_placement_snapshots.php`), but no weight.
- **Where weight lives (PROPOSAL):** keep `catalog_variations.weight_grams` (integer grams, NULL = unknown). No new weight table. Unit: grams in storage; the admin field is ONE field «Тегло, грамове» (whole number 1…100 000) with a hint «1 кг = 1000». (Couriers price by bands, e.g. ≤ 1 kg, ≤ 3 kg: integers in grams make band tests exact.)
- **Product-level default with per-variation override: yes, but as a UI convenience, not a second stored truth.** A garment's size variations differ by tens of grams, but the courier bands are coarse; typing one weight for the whole product and overriding a few variations is what the merchant will want. PROPOSAL: the variations grid gets «Тегло (г)» per row plus a top-of-tab «Тегло за всички варианти» mass field (the same `edit_all` pattern as the price fields, `EditVariableProduct.php:1165-1190`) that WRITES the value into every variation without one. No `catalog_products.weight_grams` column: «unknown» must stay unambiguous (a default that silently applies would make an unweighed variation look weighed).
- **Order snapshot: YES, capture it at checkout.** The waybill needs the weight of what was SOLD; the product can change afterwards. PROPOSAL: a nullable `unit_weight_grams` on `operational_sales_sale_lines` (next to the other snapshot fields, filled by `SaleLineSnapshotBuilder`) and a nullable `parcel_weight_grams` on `orders` + `order_placement_snapshots` = the sum when EVERY line is known, else NULL (the same all-or-nothing rule as `ShippingQuoteService:256-266`). Both are append-only facts (CLAUDE.md rule 4: a sale line is immutable). Existing orders stay NULL (unknown), which the shipping layer already understands.
- **Dimensions:** the three `*_mm` columns exist too and couriers want them for some services; out of scope here, but the same admin row can take them later without a migration.

## C. Sections

- **How a P4b source works.** `SectionSet::SOURCES` is the closed list (`SectionSet.php:34`; `validate()` `:88`, strict `read()` `:147`, `section()` `:177`, source check `:219`). `SectionCompiler` turns the definitions into the compiled document with the per-source shape (`SectionCompiler.php:46-55,139-175`; `blocks` re-cleaned when read, `:169-174`). `SectionResolver::resolve()` builds each section's HTML per product with a `match` on the source (`SectionResolver.php:41-49`) and drops empty ones (`:51-53`; `blocks` / `meta` count as empty when their HTML is `''`). The printing views are the accordion / tabs partials (`partials/summary/accordion.blade.php`, `partials/product-tabs.blade.php`). The admin source dropdown is `SectionsZone.php:163-164` with the labels `design.sections.sources.*` (bg + en).
- **PROPOSAL: a new source `measurements`** (label «Таблица с размери» / «Size table»). Added to `SOURCES`; no stored text, no blocks (the section is only a title + the source). A `measurements => MeasurementTable::html($data)` arm in `SectionResolver`; the table is built by one small pure class (`App\Storefront\Measurements\MeasurementTable`) that outputs the `sf-table-wrap` markup of TBL-1 itself (`<div class="sf-table-wrap"><table>…`, escaped text, `th scope`, a first-column `th scope="row"`), so the look, the phone scroll, the sticky first column and the shadow are inherited from `resources/css/storefront.css` (TBL-1 block) with no new CSS beyond maybe a caption.
- **Reads and statements.** The page must read nothing for a product with no template. Therefore `catalog_products.measurement_template_id` (nullable FK, `nullOnDelete`) is added to the select of `CatalogReader::product()` (the row the page already loads: 0 statements) and carried on `ProductPage` / `ProductContext` (the same one-instance mechanism P7-3 added). `ProductController` asks `MeasurementReader::forProduct($id, $templateId)` **only when** the template id is not null AND a published section has source `measurements` (the compiled document already says so for free: `SectionCompiler::published()`); then ONE statement reads the template's measures + the product's values in one joined, ordered query, and the row labels come from the product's axis values, which `product()` has already loaded (`$optionValues`, `CatalogReader.php` ~l.119-130; the size axis is chosen by the flag of §A). So: no template / no section ⇒ **0** statements; template + section ⇒ **+1** (maybe +2 if the row labels need `catalog_attribute_values.sort_order`: that column can ride in the same join). The pinned product-page numbers (22 reader-only, 27 real, and the ones of `StorefrontPageQueryCountTest`) are not touched for products without a template; a pinned test is added for «with template» (as P7-3 did for badges).
- **Empty cells / rows / columns.** A column whose every cell is empty is dropped; a row (size) whose every cell is empty is dropped; if nothing is left the section returns `''` and is not printed (the `blocks` rule). Rows only for sizes the product SHOWS (the shown variations' values; a size with no shown variation is not printed even if it has numbers).
- **Hidden-not-deleted numbers.** The reader joins on the product's CURRENT template, so numbers stored for another template are simply not selected (see §E.5).

## D. Admin

**Where things live today.**
- Product resource `app/Filament/Resources/ProductResource.php` (3 547 lines): `form()` with the Tabs «Общи / Атрибути / Цена и наличност / Информация» (`:298-312`), the «Информация» tab `sectionTextsTab()` (`:239-262`, one rich-text per section whose source takes a product text, plus the per-product switch «Показвай на този продукт»). The variable product's edit page overrides `form()` (`EditVariableProduct.php:387-444`: General, Attributes, Axes, Variations, Information; the tab ids are explicit, `:?tab=` deep links). The simple product page is `EditProduct.php` (the universal variation's `barcode` / `is_purchasable` are loaded at `:118-123`).

**PROPOSAL.**
1. **Two catalog resources in «Каталог»:** «Показатели» (measures: name, unit, sort order, active) and «Шаблони за размери» (templates). Both are the plain resource style of `SeasonResource` / `ProductGroupResource` (a list, create / edit, delete with the rules of §E.3, `AuthorizesViaStaffPermission` with the existing catalog permission, activity log on every write). The template form: a name + a `Repeater` of measures (a `Select` of the measure list, reorderable with buttons, each measure at most once, 1…20 measures). Narrow fields and info icons per `admin-ui-standard.md`.
2. **Product edit:** a new tab «Размери» (explicit id `measurements`, after «Вариации»; on the simple page after «Цена и наличност»), visible only when at least one template exists. Content: (a) a `Select` «Шаблон за размери» (blank = none; changing it with numbers present for the OLD template shows the warning of §E.5), (b) a grid. **Recommendation: a Filament `Repeater` is wrong here** (rows × a dynamic number of columns, tab-through typing needed); use a **fixed-row `Repeater`-less grid built from `TextInput`s in a `Grid`** keyed `measure_values.<rowKey>.<measureId>`: the number of cells is (rows ≤ ~20) × (measures ≤ 20), well below the point where a custom Livewire table pays off, it validates and saves with the form like every other field, and Tab moves across it. Each cell is a `numeric` input (step 0.01, min 0, max 99 999.99). Row headers are read-only text (the size value); the unit is shown in the column header. «Копирай от друг продукт» is a header action with a product picker (the existing product `Select` search), copying by matching size value (§E.5). The whole tab is gated by `PRODUCT_MANAGE` like the Axes tab (`EditVariableProduct.php:447-450`).
3. **Weight:** a column «Тегло (г)» in each row of the variations `Repeater` (`:1291`, next to `cost` / `stock_quantity`, i.e. around `:1529-1537`), written in `updateVariationRows()` (`:3044`) with the same `logFieldChanged` pattern through `Variation::setDimensions($grams, $l, $w, $h)` keeping the other three values; plus the «Тегло за всички варианти» mass field at the top (`:1165-1190` pattern). For a simple product: one field next to the shipping-class select in the General tab (`ProductResource::shippingClassSelect()`, `:1062`; the universal variation is `EditProduct.php:122`). Plain integer, whole grams, empty = unknown, min 1, max 100 000.
4. **Axis attribute screen:** one checkbox «Показател за размер» on the attribute definition (§A).

## E. Storage proposal

All new tables belong to `packages/EasyCo/Catalog` (a measurement is catalog data; no other domain depends on it — rule 9), with `catalog_` names and explicit short index names (rule 5: every name ≤ 64 chars is checked up front).

### E.1 Tables
- `catalog_measures`: `id`, `name` (string 80, unique), `unit` (string 8, closed list, see §F), `sort_order`, `is_active` (bool, default true), timestamps. «Archive» rather than delete once used (§E.3).
- `catalog_measurement_templates`: `id`, `name` (string 80, unique), `sort_order`, timestamps.
- `catalog_measurement_template_measures`: `template_id` (FK cascade), `measure_id` (FK **restrict**), `sort_order`; unique (`template_id`, `measure_id`) with a short name.
- `catalog_measurement_values`: `id`, `product_id` (FK cascade), `row_value_id` (FK `catalog_attribute_values`, **restrict**, NULL for a simple product's single row), `measure_id` (FK restrict), `value_hundredths` (unsigned int; 0 is a real value, an absent row = empty), timestamps. Unique (`product_id`, `row_slot`, `measure_id`) where `row_slot` is a STORED generated column `COALESCE(row_value_id, 0)` so the NULL row of a simple product is unique too (MySQL / MariaDB and SQLite ≥ 3.31 both support it; MEAS-2 starts with a spike on both — rule 3 / rule 2: if the generated column is refused on the test DB, fall back to one extra non-null `row_slot` column filled by the writer).
- `catalog_products.measurement_template_id` (nullable FK, `nullOnDelete`, short index). The numbers are keyed by product + size value + **measure**, not by template: that is what makes «switch template, keep the numbers» true — the numbers of a measure that the new template also has are even reused (a «Гръдна обиколка» typed under «Блузи» shows again under «Рокли»).
- `catalog_attribute_definitions.is_size` (bool default false).
- Weight: `catalog_variations.weight_grams` exists; sale snapshots: `operational_sales_sale_lines.unit_weight_grams`, `orders.parcel_weight_grams`, `order_placement_snapshots.parcel_weight_grams` (all nullable; one migration each, in their packages).
- Constraint check: every correctness invariant above (uniqueness of a value cell, every reference) is a real DB constraint (rule 2); the single non-DB rule is «row_value_id belongs to an axis of this product», enforced in the writer (a pivot cannot express it) and by the delete rule below.

### E.2 Layering and writers
Domain classes stay pure (rule 1): `Measure`, `MeasurementTemplate`, a `MeasurementValue` value object (hundredths), contracts `MeasureRepository`, `MeasurementTemplateRepository`, `MeasurementValueRepository` in `packages/EasyCo/Catalog/src`, Eloquent implementations in `Persistence/Eloquent`. App-layer writers in `app/Services` in the style of `ShippingMethodWriter`: transaction, `ActivityLogger` (`logCreated` / `logFieldChanged` / `logDeleted`, entity types `measure`, `measurement_template`, field names like `measurement[<size>].<measure>`), and **hooks after commit** (CLAUDE.md rule 10: domain packages never call `Hook`). Hook names (the existing `catalog.*` convention is `catalog.product.slug`, `catalog.variation.sku`, `catalog.variation.barcode` filters): actions `catalog.measure.created|updated|archived|deleted`, `catalog.measurement_template.created|updated|deleted`, `catalog.product.measurements.saved` (product id) — added to the Hook Reference in the same commit.

### E.3 Delete rules (rule 4: history is never destroyed)
- **A measure** referenced by a template or by values: cannot be hard-deleted (`restrictOnDelete`); the admin offers **Archive** (`is_active = false`): it disappears from the pickers and the grids' column choices and is NOT printed on the storefront any more (the merchant retired it; open question 5); its numbers stay in the table. Hard delete only when unused by any template and any value. Measurements are configuration, not financial history (no sale line references them), so they are NOT protected by rule 4's strong form, but nothing is silently dropped.
- **A template** in use by products: delete is refused with the count («Използва се от 14 продукта») and a link to the list filter; unused templates may be deleted. Removing a measure from a used template is allowed after a warning with the count; the numbers stay in `catalog_measurement_values` (hidden).
- **A size value** (`catalog_attribute_values`) is already RESTRICT-protected by variations; values with measurement rows add one more restrict reason, shown in the existing deletion-impact view if the attribute-value screens have one.
- **Deleting a product:** values cascade with the product (a hard product delete is already restricted by history elsewhere, `CatalogDeletion`).

### E.4 Duplicate, mass edit, import
- **Duplicate product** (`DuplicateProduct`): a SIMPLE duplicate copies the template id and the single row's numbers (descriptive, not unique, like the description it already copies); a VARIABLE duplicate copies the template id only (it starts with zero axes, so no size rows exist yet); the numbers are then one click away through «Копирай от друг продукт» once the axes are declared again, matching by size-value id. Weight is NOT copied (a barcode precedent: a physical fact of a different product), except the simple product's: PROPOSAL copy it, because a duplicate is usually a sibling of the same garment — flag as an open point in the doc of MEAS-5.
- **Mass edit (P6d):** one new operation `set_measurement_template` (the pattern of `SET_SEASON`/`SET_GROUP`, `ProductMassEditor.php:63-65`): sets / clears the template id for the selection; it never writes numbers. A mass «set weight» operation is a separate later one.
- **Import from the old shop:** nothing is needed now; the writers take `(product, size value, measure, hundredths)` so a one-off command can fill the tables. Measure names + units are the real work: the old shop's list is the seed.

### E.5 The three agreed ideas — feasibility
- **Switch a template with numbers filled → keep them (hidden) after a warning: feasible and free** with the storage above: the numbers are keyed by measure, the reader and the grid show only the CURRENT template's measures. The warning lists how many typed numbers would be hidden (measures not in the new template). Nothing is deleted. A «Изчисти числата, които не са в шаблона» action is optional.
- **Add a measure to a used template → an empty column appears:** feasible (a template row is added; every product of that template simply has no cells for it; empty columns are not printed on the storefront until typed).
- **«Копирай от друг продукт»:** feasible; copies the source product's numbers (and template id) into the grid state for the rows whose size value matches (by `attribute_value_id`, else by exact value text), never writes until «Запази», logs one activity row.

## F. Units

- **Closed list** (code → admin label): length `mm`, `cm`, `m`, `in`, `ft`. Weight is NOT a measure unit (it is the variation's `weight_grams`). One unit per measure, fixed when the measure is created (changing the unit of a measure that has numbers is refused: a number in cm must not become a number in inches; the merchant makes a new measure). Closed list in a PHP enum + validated on write and on read (rule: closed lists everywhere on the storefront).
- **Decimals:** store as **integer hundredths** (`value_hundredths`, 95.5 cm = 9550): no float drift (the reasoning `Variation::setDimensions()` already gives for integers, `Variation.php:407-412`), exact equality, sortable. Admin input: a decimal with at most 2 decimals, 0 < value ≤ 99 999.99 (0 is refused as «no value»: leave it empty). A DECIMAL column would also be exact, but integer hundredths match the project's Money posture (`minor` units) and avoid string/float casting in PHP.
- **Display:** through the store locale like prices (`PriceDisplayFormatter`-style formatter; bg: decimal comma «95,5», en: dot), trailing zeros trimmed («90», «95,5», «95,25»), no thousands separator below 10 000. The column header is `name, unit` («Гръдна обиколка, см»), escaped.

## G. Security and validation

- Closed lists: units (enum), measure ids and template ids (exist-checked), row value ids (must belong to an axis of THIS product, checked in the writer), booleans.
- Ranges: names 1…80 plain text (`App\Rules\PlainText`, as the badges and blocks do), a template 1…20 measures, a measure at most once per template, a value 0 < v ≤ 99 999.99, 2 decimals max; a tampered form with an unknown id is refused as a field error and nothing is written (the `BadgeSet` posture).
- Storefront: the table is built by one PHP class, every text goes through `e()`, no `style=`, no class from data, no script, no inline handler (the classes are the fixed `sf-table-wrap` + the cell tags); `th scope` only `row|col`, matching the TBL-1 sanitizer so that printing it through `HtmlBlockSanitizer::render` would be a no-op; the section HTML is NOT run through the description sanitizer's DOM walk (it is built, not stored), but a test asserts it passes `HtmlBlockSanitizer::clean` unchanged.
- Permissions: measures / templates under the catalog permission, the product tab and the weight field under `PRODUCT_MANAGE`; the storefront reads published data only (the section is part of the compiled sections document; the numbers are public).
- The weight is never read by the storefront readers: the product page select, `ProductPage`, the listing and the JSON contract do not carry it (tests assert the key is absent from `toArray()` and from the page HTML).

## I. Open questions for the owner (recommendation first)

1. **Which axis is «the size» when a product has size + colour?** Recommended: one checkbox «Показател за размер» on the attribute (set once), rows = one per size value, colours share the numbers. (Alternative: rows per variation, i.e. the same numbers typed once per colour.)
2. **Weight unit in the admin:** grams as a whole number («350») or kilograms with a decimal («0,35»)? Recommended: grams (exact, couriers' bands are in kg but the sum of garments is easier in grams); the order snapshot and the courier feed always use grams.
3. **Default weight per product:** recommended «Тегло за всички варианти» as a convenience that writes into the variations without a weight (not a stored product default, so «unknown» stays unambiguous). Do you also want the same for a whole CATEGORY later (e.g. every T-shirt 200 g)?
4. **Measure units list:** recommended `mm, cm, m, in, ft` (a unit cannot be changed once numbers exist). Anything else you need (e.g. a size label such as «EU 38» as a text column, which is not a number)?
5. **When a measure is archived, do the numbers stop printing on the storefront?** Recommended yes (archive = «we no longer show this»); the numbers stay stored and come back if the measure is un-archived.

## Owner decisions (2026-11-13)

Answers to §I. They replace the "recommended" wording there.

1. **Size axis** = a checkbox «Показател за размер» on the attribute definition (MEAS-2/3, not MEAS-1).
2. **Weight in whole GRAMS** in the admin («350»), hint «1 кг = 1000 г». Storage, snapshots and the courier feed are grams.
3. **«Тегло за всички варианти»** is a convenience that writes into the variations WITHOUT a weight; no stored product-level default. A category-level weight: not now.
4. **Units** of the measures: `mm, cm, m, in, ft` (MEAS-2/3).
5. **An archived measure stops printing** on the storefront (MEAS-3/5); its numbers stay stored.

The weight is NEVER shown on the storefront. It is for the later courier integration (waybills priced by weight bands).

## As built (MEAS-1): variation weight in the admin + weight snapshot at the sale

**Admin (section A).**
- One shared field, `ProductResource::weightGramsInput()` («Тегло (г)», whole number 1…100 000, empty = unknown/NULL, info icon `InfoHint` with bg + en text in `products.fields.weight_grams_help`). A disabled field (no `PRODUCT_MANAGE`) is not submitted, so a missing key means "no change".
- Variable product: the field is in every row of the `existing_variations` Repeater (next to cost / stock); `updateVariationRows()` writes it inside the `PRODUCT_MANAGE` block. «Тегло за всички варианти» (`bulk_weight_grams`, visible with «Редактирай всички», not submitted) fills, on blur, ONLY the rows whose weight box is empty; what is typed in a row stays; the rows are then saved like any other value, so the log has one entry per variation changed.
- Simple product: the same field after the shipping-class select (`priceStockTabComponents()`, shared by create and edit); `EditProduct` and `CreateProduct` write it to the universal variation.
- ONE writer, `App\Services\VariationWeightWriter`: goes through the EXISTING `Variation::setDimensions($grams, $length, $width, $height)` keeping the three dimensions as they are (the frozen `Variation.php` is not edited), logs `weight_grams` (simple) / `variation[<id>].weight_grams` (variable) old → new through `ActivityLogger::logFieldChanged`, and re-validates the range and "whole digits only" so a tampered submission never reaches storage.
- Duplicate: a SIMPLE duplicate copies the weight (not the dimensions); a variable duplicate has no variations (unchanged).
- NOT done: the variable-product CREATION wizard has no per-variation price/stock grid with weight (its rows are sku / barcode / active / class only), so no weight column was added there; the edit page is enough, as the task allowed.

**Snapshot at the sale (section B).** Three nullable unsigned integer columns, no index (nothing filters by them, so no identifier-length risk): `operational_sales_sale_lines.unit_weight_grams`, `orders.parcel_weight_grams`, `order_placement_snapshots.parcel_weight_grams` (one migration in OperationalSales, one in Order; idempotent). `SaleLine` (OperationalSales, not a frozen file) carries `unitWeightGrams` as an optional trailing constructor / `create()` / `reconstituteFromStorage()` argument (SALE lines only; the other factories and the refund / reversal lines leave it NULL), `Order` carries `parcelWeightGrams` the same way; the mapper / repository / models persist them. `SaleLineSnapshotBuilder` reads the weight from the SAME `VariationRepository::findByIds()` call the sold attributes already use (`VariationDisplayReader::soldSnapshotFor()`), so no statement is added. The order's parcel weight is `ParcelWeight::sum()` over the built sale lines: the ONE all-or-nothing rule (one unknown weight ⇒ NULL, never 0), now also used by `ShippingQuoteService::context()` (its behaviour and tests are unchanged). Existing orders stay NULL; nothing refuses a checkout for a missing weight. Admin order view: «Тегло на пратката: 1,32 кг» (or «—») in the «Плащане и доставка» block (`OrderResource::parcelWeightLabel()`).

**Known limits (reported, not fixed).** A line ADDED or changed later through the order editor (`OrderLineEditor`) has NO weight snapshot and the order's `parcel_weight_grams` is not recomputed by an edit: it is the weight of the order as placed. A courier feed (MEAS-6) that needs the weight of an edited order must recompute from the lines, or a later task must extend the editor.
