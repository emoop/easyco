# No admin/staff auth guard exists — every merchant-facing endpoint is currently unprotected

**Status:** Note only. Nothing here is built yet. Recorded because it was discovered by directly auditing routes/api.php's middleware, not assumed, and must be closed before any real deployment — not something to rediscover late.

**The gap, confirmed directly:** grep the actual middleware on every route in routes/api.php. Exactly two routes are protected (`POST /account/logout`, `GET /account/me`, both behind `auth:customer`). Every other route — `POST /promotions`, `POST /brands`, `POST /categories`, `POST /tags`, `POST /products`, `PUT /products/{productId}/brand`, every attach/detach endpoint for product categories/tags, `PUT /cart/promotion`'s companion promotion-creation surface — has no authentication at all. Anyone who knows the URL can call `POST /promotions` and create an arbitrary discount code, or `POST /products` and create arbitrary catalog entries, with zero credentials.

**Why it happened, not as an excuse but so it isn't repeated by accident:** every merchant-facing controller built this session deliberately mirrored `AttributeDefinitionController`'s intentionally minimal style — "no auth, no form request class, no resource transformer" — for speed while the domain layer was still taking shape. That was a reasonable tradeoff for a dev-only phase. It is not a reasonable state for anything reachable by the public.

**What's needed before any real deployment:**
- A new `staff`/`admin` auth guard, separate from the existing `customer` guard — mirrors how `Account`'s own `account-domain-design.md` already established a dedicated, separate guard for customer identity specifically so logging in as a customer never doubles as logging in anywhere else in the system. The same reasoning applies in reverse: a staff/admin session must never double as a customer session either.
- Every merchant-facing endpoint built so far needs to move behind that guard: all of `/promotions*`, `/brands`, `/categories`, `/tags`, `/products` (creation and all sub-resource attach/detach/update routes), `/attribute-definitions`, `/attribute-values`, `/media` (the standalone upload endpoint).
- `/cart/*` and any future Checkout/Order-placement routes stay customer-facing (or guest-accessible) — this note is specifically about the merchant/administrative surface, not the shopper-facing one.
- Whatever staff-account model backs this guard doesn't exist yet either — this note doesn't presume its shape (a separate `Staff` entity? roles/permissions from day one, or a single flat "is staff" flag for V1? — an open question for whenever this is actually designed), only that the gap exists and must be closed deliberately, not accidentally inherited from a "no auth for speed" pattern that was never meant to reach production.
